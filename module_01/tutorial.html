Concept 1 — Why Environment Matters More Than You Think

Security research — especially PhD-level research — requires you to be able to reproduce attacks reliably, vary one parameter at a time, and observe the exact outcome. This is the scientific method applied to software. A sloppy lab environment produces sloppy conclusions: "it worked sometimes" is not a publishable result. "It works under exactly these conditions, and here is why" is.

XSS is particularly tricky to study in the wild: real websites have WAFs, CDNs, rate limiting, and legal restrictions. Your local lab removes every variable except the one you are studying. When a payload fires in your lab, you know exactly why it fired. When it doesn't, you know exactly what stopped it. That precision is the foundation of a strong threat model — the core artifact of your PhD work.

We run two servers in parallel — Python/Flask and Node.js/Express — because this immediately teaches you something important: XSS is a browser-side vulnerability. Both servers produce the same HTML; both are equally vulnerable; both require the same fix. The attack surface lives in the browser's HTML parser and JavaScript engine, not in Flask or Express. Your defense will need to work at that level too.

Core Insight The browser is a document-execution engine. It was designed in the 1990s to display documents, then progressively extended to run programs. Every XSS vulnerability in this course is, at its root, the browser faithfully executing instructions it found in a document — instructions the attacker placed there because the application failed to distinguish between data and code. Keep this distinction in mind across every module: data/code confusion is the root cause, everything else is a consequence.

The tools we install in this module are not optional accessories. They are the lenses through which you will observe every attack in this course. Browser DevTools lets you see the DOM as the browser constructed it — which is not the same as the HTML the server sent. Burp Suite lets you intercept and modify requests in flight, so you can inject payloads without touching any source code. Understanding these tools at a deep level is what separates a researcher who can find novel XSS from one who can only reproduce known examples.

Concept 3 — Browser DevTools as a Security Instrument

Browser DevTools (F12 in Chrome and Firefox) was designed for web developers, but every feature has a direct security research application. You need to be fluent in four panels before Module 02:

The Elements Panel — Your Live DOM Inspector

The Elements panel shows you the DOM as the browser constructed it, not as the server sent it. This distinction is everything in XSS research. If a server sends <p>Hello <b>World (missing closing tags), the browser silently fixes it. The Elements panel shows you the corrected tree. When you inject a payload into a page, the Elements panel is where you verify whether your payload was parsed the way you intended, got filtered, got encoded, or mutated into something else.

Right-click any element → "Edit as HTML" lets you test payloads directly in the live DOM without touching the server. This is how you confirm a payload works before trying to get it past a filter.

The Console Panel — Your JavaScript Execution Environment

The Console runs arbitrary JavaScript in the context of the current page. This is exactly what XSS does — it injects JavaScript that runs in the victim's page context. Use the Console to prototype payloads: document.cookie shows you what cookies are accessible, document.domain confirms what origin you are on, window.location shows the full URL. Before you ever inject a payload into a form field, test it in the Console first.

The Network Panel — Your Request/Response Inspector

The Network panel captures every HTTP request and response. Click any request to see the exact headers sent and received. This matters for XSS because: the Content-Type response header tells the browser how to parse the response (HTML? JSON? plain text?); the Set-Cookie header shows which cookies have HttpOnly (not accessible to JS) and SameSite attributes; and Content-Security-Policy headers (when present) tell you which scripts the page allows to run. Each of these is a defensive control — or the absence of one.

The Sources Panel — Your JavaScript Debugger

The Sources panel lets you set breakpoints on any line of JavaScript running in the page. In DOM XSS (Module 09), you will use this to pause execution at the exact moment attacker-controlled data reaches a dangerous sink like innerHTML or eval(). Without breakpoints, DOM XSS can be invisible — the payload executes and disappears with no network request to capture. The Sources panel makes it observable.

Warning — Do Not Test on Live Sites Every payload in this course fires alert(document.domain) or alert(document.cookie) as a proof-of-concept. These are benign. However, testing XSS payloads against websites you do not own — even to report a bug — without explicit written permission is illegal in most jurisdictions under the Computer Fraud and Abuse Act (US), the Computer Misuse Act (UK), and equivalent laws elsewhere. Your local lab is the only safe environment for this course. If you want to practice on intentionally vulnerable external platforms, use PortSwigger Web Security Academy (free, legal, purpose-built).

Concept 4 — How to Think Like an Attacker (The Attacker's Questions)

Defenders who were never attackers tend to think about XSS as a list of strings to block. Attackers think about XSS as a set of questions to answer about the target. Learning to ask these questions is the single most important skill in this course — it is what will make your PhD defense contributions novel, because you will be able to identify the assumptions that current defenses make and precisely characterize where those assumptions break down.

Every time you encounter any user-supplied input that appears in a web page, ask yourself these five questions in order:

Question 1: In which HTML context does my input land?

HTML has multiple distinct parsing contexts. The same character has different meanings in different contexts. A < in the body context starts a tag. In an attribute value context inside double quotes, it is harmless data (but a " would break out of the attribute). In a script context (inside <script> tags), neither < nor " alone enables execution — but a </script> sequence closes the script block. In a style context, only CSS is parsed. The injection technique always depends on the context. We dedicate Module 02 to parser contexts entirely.

Question 2: What characters are available to me?

Some applications filter specific characters. < and > are often HTML-encoded to &lt; and &gt;. Single and double quotes may be stripped or escaped. Each available character opens or closes specific attack paths. When you cannot use <, you cannot create new tags — but you may still be able to inject attributes into existing tags. When you cannot use quotes, you may still be able to use unquoted attribute values. The attacker's job is to find the maximal capability within the character set they have available.

Question 3: What mechanism can I reach with those characters?

Module 03 introduces the five execution mechanisms that cover every XSS attack ever documented. Given a context and a character set, one or more of those mechanisms may be reachable. The attacker systematically works through them. A thorough defender must ensure all five are addressed.

Question 4: What does execution give the attacker?

Executing alert(1) proves the XSS is real. But the actual payload depends on the goal: stealing cookies, forging requests, capturing credentials, persisting via Service Workers, or pivoting to internal networks. Understanding what execution buys the attacker is what lets you calculate the true severity of a vulnerability — which is what a threat model must state precisely.

Question 5: What defense is present, and what is its blind spot?

No defense currently deployed covers all five execution mechanisms under all conditions. Every defense has assumptions, and assumptions have blind spots. The attacker's final question is: "given the defenses I can observe (CSP headers, cookie flags, input filters), what is still reachable?" Module 17 studies each defense's coverage. Module 18 is specifically about mapping that coverage to the five mechanisms so your intervention can claim — with evidence — that it closes a specific gap.

PhD Insight — Threat Model Framing In your paper, a threat model is a precise statement of: (1) what the attacker can control, (2) what they cannot control, (3) what the defender's goal is, and (4) under what conditions a defense succeeds or fails. The five attacker questions above map directly onto this structure. When you finish Module 18 and write your threat model, you will have empirical evidence from this lab — real payloads that worked and real defenses that stopped or failed to stop them — to support every claim.

Code Walkthrough — lab_server.py

lab_server.py
"""
XSS Mastery Lab — Module 01
Flask lab server: minimal home page only.
"""

from flask import Flask, send_from_directory
import os

# Flask() needs __name__ so it knows where to find the 'public/' folder.
# static_folder="public" tells Flask to serve files from ./public/ directly.
app = Flask(__name__, static_folder="public")

@app.route("/")
def home():
    # send_from_directory is safe — it prevents path traversal attacks.
    # (os.path.join + open() would be vulnerable to ../../etc/passwd.)
    # We will rely on this safety in later modules too.
    return send_from_directory("public", "index.html")

@app.route("/ping")
def ping():
    # Health check — returns JSON. We will use this from scripts in M11+.
    # Flask auto-sets Content-Type: application/json for dict returns.
    return {"status": "ok", "module": 1}

if __name__ == "__main__":
    port = int(os.environ.get("PORT", 5000))
    # debug=True: auto-reload on file changes + detailed error pages.
    # SECURITY NOTE: debug=True in production = remote code execution.
    # Werkzeug's debugger PIN protects it locally but never deploy this.
    app.run(host="0.0.0.0", port=port, debug=True)

Code Walkthrough — lab_server.js

lab_server.js
const express = require("express");
const path    = require("path");

const app  = express();
const PORT = process.env.PORT || 5000;

// express.static serves every file inside /public directly.
// It sets Content-Type headers automatically based on file extension.
// Correct Content-Type is a defence: serving .svg as image/svg+xml
// prevents the browser treating it as HTML. We exploit this in Module 07.
app.use(express.static(path.join(__dirname, "public")));

// Parse URL-encoded form bodies — needed from Module 04 onward.
// extended:false uses the built-in querystring library (no prototype pollution).
// extended:true uses qs, which supports nested objects but has had CVEs.
app.use(express.urlencoded({ extended: false }));

// Parse JSON request bodies — needed from Module 09 onward.
app.use(express.json());

app.get("/", (req, res) => {
    // sendFile requires an absolute path — path.join(__dirname, ...) ensures that.
    res.sendFile(path.join(__dirname, "public", "index.html"));
});

app.get("/ping", (req, res) => {
    // res.json() sets Content-Type: application/json automatically.
    res.json({ status: "ok", module: 1 });
});

app.listen(PORT, () => {
    console.log(`\n  XSS Mastery Lab — Module 01`);
    console.log(`  Listening on http://localhost:${PORT}`);
});
Tip — Why two middlewares (urlencoded + json)? Express does not parse request bodies by default — you must opt in. We add both parsers now so every future module can receive either form submissions or JSON API calls without changing the server setup. Notice the extended: false choice — this is a security decision. The qs library (extended: true) supports nested object syntax which has historically enabled prototype pollution attacks. We use the safer flat parser and switch in Module 14 to study exactly that attack.

Configuring DevTools (do this now)

  1. Open Chrome at http://localhost:5000. Press F12.
  2. In the DevTools top bar, click the ⚙ gear icon (Settings). Under Preferences → Sources, enable "Enable JavaScript source maps" and "Pause on caught exceptions".
  3. In the Network panel, check "Disable cache" (top-left checkbox). Leave this on always during this course — stale cache hides whether your attack or your fix actually reached the browser.
  4. In the Console panel, click the filter icon and ensure All levels are shown. XSS payloads sometimes produce CSP violation reports as console errors — you want to see them.
  5. Type document.domain in the Console and press Enter. You should see localhost. This is the origin context any injected JavaScript would run in.

Exercises

Warm-up

Exercise 1 — Confirm Your Lab Is Alive

Start either the Flask or Node server. In Chrome DevTools Console, navigate to http://localhost:5000 and run: 

fetch('/ping').then(r => r.json()).then(console.log)

You should see {module: 1, status: "ok"} logged. Then open the Network panel and find the /ping request. What is the Content-Type of the response? What does that tell the browser about how to interpret the response body?

Warm-up

Exercise 2 — Read the DOM, Not the Source

View the source of http://localhost:5000 (Ctrl+U in Chrome). Then open DevTools Elements panel and compare the two views. Are they identical? Open your browser on any real website (your university homepage, for example) and repeat the comparison. Note at least two differences between the raw HTML source and the live DOM. Write down why those differences matter to an attacker.

Core

Exercise 3 — Modify the Lab Home Page

Open public/index.html in VS Code. Add a fourth card to the grid that links to /module_01/tutorial.html and shows the title "Module 01 — Tutorial". Save the file. If using Flask, the server auto-reloads. If using Node with nodemon, it also auto-reloads. Refresh the browser. Confirm the new card appears.

Then: right-click the new card in Chrome → Inspect. In the Elements panel, double-click the card's text and change it to something else. Press Enter. Notice the page changed without reloading. Now reload the page. The change is gone. Explain in writing: where did your change live, and why did reload erase it? (Hint: this is the difference between the live DOM and the server source — and it is directly relevant to how DOM XSS works.)

Core

Exercise 4 — Intercept a Request with Burp Suite

Open Burp Suite Community. Go to Proxy → Intercept and turn interception ON. Configure Chrome to use Burp as an HTTP proxy (Settings → Search "proxy" → Manual proxy: 127.0.0.1:8080). Navigate to http://localhost:5000/ping in Chrome. Burp intercepts the request. In the Intercept panel, change the URL path from /ping to /anything-you-like and forward the request. What does the server return? What HTTP status code?

This is the core of how attackers inject payloads: they intercept a legitimate request and modify it before it reaches the server. You will use Burp this way in every module from Module 04 onward.

Stretch

Exercise 5 — Add a Custom Response Header

Modify both lab_server.py and lab_server.js to add a custom HTTP response header to every response: X-XSS-Mastery-Module: 01. Verify it appears in the Network panel for both / and /ping.

Then research and answer in writing:

  • What is the X-Content-Type-Options: nosniff header and why does it matter for XSS?
  • What is X-Frame-Options and how does it relate to clickjacking (which chains with XSS)?
  • Add both of these headers to your servers. Verify them in Burp Suite's response view.

In Flask: use @app.after_request. In Express: use app.use((req, res, next) => { res.setHeader(...); next(); }).

What's Next

Module 02 — How Browsers Parse HTML: The Attack Surface

The lab is running and your tools are configured. Module 02 introduces parser_demo.html — a page that deliberately feeds malformed, ambiguous, and adversarial HTML to the browser and visualises how the parser recovers. You will see with your own eyes that the browser does not reject broken HTML — it silently repairs it according to a spec that runs to hundreds of pages. That repair process is the mechanism that makes XSS possible: the attacker writes something that looks broken to a filter but is perfectly valid to the parser. Understanding this is not optional background knowledge. It is the foundation every attack in this course is built on.
