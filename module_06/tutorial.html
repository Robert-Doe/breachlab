Module 06 of 19

URI Scheme Injection:
Mechanism 3 in Depth

The third execution mechanism requires no HTML tag injection at all. When a URL value is attacker-controlled and flows into a navigation context — an href, an action, a redirect header, or a DOM location assignment — the javascript: scheme turns that URL into a JavaScript executor running in the victim's origin.

Prerequisites

Modules 01–05 complete. You have fired tag injection and event-handler payloads. You understand the browser's HTML parsing pipeline and the five execution mechanisms framework.

What you will build in this module
  • An open redirect endpoint (/redirect) with no scheme validation
  • A link-preview endpoint (/link-preview) that injects user URLs into href
  • A profile page (/profile) with three simultaneous URL injection points
  • An interactive attack demo with 7 steps including obfuscation bypasses
  • A searchable URI scheme reference covering all dangerous schemes and attributes

Concept 1 — The URL as an Execution Context

HTML has two fundamentally different ways of embedding executable content. The first is the element/attribute model — a tag exists in the DOM and an event fires on it. Modules 04 and 05 covered this model. The second is the navigation model — the browser is asked to navigate to a resource identified by a URL.

When the URL scheme is http: or https:, the browser fetches a remote resource. When the scheme is javascript:, the browser evaluates the expression that follows and uses the result as the new document content. When the scheme is data:, the browser renders the inline document specified.

These URI schemes are not XSS quirks — they are defined behaviour in the HTML and URL specifications. The vulnerability arises when an application places attacker-controlled data into a URL-accepting context without validating the scheme. The attacker doesn't inject a tag; they inject a URL.

PhD Insight — URI Injection Crosses Injection Class Boundaries URI scheme injection is unique in that it can manifest as reflected, stored, or DOM-based XSS depending on where the URL value originates. A stored profile website field that gets rendered into an href is stored XSS via URI mechanism. An open redirect that reflects ?url= into a Location header is reflected XSS via URI mechanism. A client-side router that reads location.hash and assigns it to location.href is DOM-based XSS via URI mechanism. The mechanism taxonomy (Module 03) captures this; the origin taxonomy (reflected/stored/DOM) does not. Both are needed for a complete threat model.

Concept 2 — The javascript: Scheme

The javascript: URI scheme evaluates a JavaScript expression in the context of the current document. The expression runs with the same privileges as any other script on the page — access to document.cookie, localStorage, the DOM, and the ability to make credentialed HTTP requests to the same origin.

The scheme is triggered by any browser navigation to a URL with that scheme. Navigation occurs via:

  • User clicking an <a href="javascript:..."> link
  • Form submission to <form action="javascript:...">
  • HTTP 3xx redirect with Location: javascript:... header
  • JavaScript assignment: location.href = "javascript:..."
  • JavaScript call: window.open("javascript:...")
  • <iframe src="javascript:..."> (browser-dependent)
  • <meta http-equiv="refresh" content="0;url=javascript:...">
Critical — href Injection Requires No HTML Injection An application that correctly HTML-encodes all output — preventing tag injection and event-handler injection — can still be vulnerable to URI injection if it places user-supplied values into href, action, or src attributes without scheme validation. The angle brackets in <a href="javascript:alert(1)"> are part of the surrounding static HTML; the only attacker-supplied string is javascript:alert(1), which contains no characters that HTML encoding would affect. Context-aware output encoding alone is insufficient — URL context requires URL scheme validation in addition to HTML encoding.

Concept 3 — The Browser URL Parser and Obfuscation

The browser normalises URLs before evaluating them. This normalisation happens after HTML parsing — meaning HTML entities are decoded first. The URL is then parsed according to the WHATWG URL Standard. The scheme component is extracted and lowercased before comparison. Leading C0 controls (tab, newline, carriage return) are stripped from the URL before parsing.

This multi-stage processing pipeline means that a filter operating at the HTML string level sees a different value than the browser URL parser eventually evaluates. The bypass chain is: 

Step 1 — HTTP request arrives:
  GET /?url=javascript:alert(1)

Step 2 — HTML encoding decode (by browser HTML parser):
  href value = javascript:alert(1)       // j → j

Step 3 — URL normalisation (by browser URL parser):
  scheme = javascript                       // lowercased, entity decoded
  path   = alert(1)

Step 4 — Execution:
  eval("alert(1)")                          // in current page origin

A filter that checks for the string "javascript:" at Step 1 sees "javascript:"
and does not match. The browser evaluates it anyway at Step 4.
Correct Defence A URL validation function must operate on the fully normalised URL value — after HTML entity decoding and whitespace stripping. The correct check is: parse the URL, extract the scheme, compare against an allowlist of safe schemes (http, https, mailto, / for relative). DOMPurify does this correctly by default. A custom filter that does a string search for "javascript:" on the raw input does not.

Concept 4 — The data: URI Scheme

data: URIs embed resource content directly in the URL. The format is data:[mediatype][;base64],<data>. When the media type is text/html, the browser renders a full HTML document — including script execution.

data: URIs that render HTML are subject to a different restriction than javascript:: they execute in a null origin rather than the origin of the current page. This means scripts inside a data: document cannot directly read document.cookie or localStorage from the parent origin via the DOM.

However, null-origin documents can:

  • Make credentialed HTTP requests to same-origin endpoints (with CORS or cookies), exfiltrating data indirectly
  • Render convincing phishing overlays that visually replace the parent page
  • Use postMessage to communicate with parent frames if the parent has an overly permissive message event listener
  • In some browser configurations, access the parent window via window.opener
PhD Insight — data: and Same-Origin Policy The null-origin restriction for data: URIs is a deliberate hardening added to modern browsers after years of abuse. Pre-2012 browsers treated data: documents as inheriting the opener's origin — giving them full same-origin access. This was a catastrophic design flaw exploited widely before the fix. The current null-origin model is safer but not harmless: the phishing and indirect-exfil vectors remain. When writing your threat model, the data: scheme requires a separate threat entry from javascript: because the impact model differs.

Code Walkthrough — /link-preview

lab_server.py — /link-preview
@app.route("/link-preview")
def link_preview():
    url   = request.args.get("url", "")
    label = request.args.get("label", "Visit link")

    # url= goes directly into href — no scheme validation.
    # HTML special chars in url ARE preserved here — the angle brackets
    # in the surrounding HTML are static. The only injected data is the
    # url value itself, which contains no HTML-special chars in a
    # javascript: payload. HTML encoding would not help here.
    #
    # Vulnerable: places arbitrary scheme in href
    # Fix: assert url.startswith(("http://","https://","/")) before using
    body = f"""<a href="{url}">{label}</a>"""

    resp = make_response(page("Link Preview", body))
    resp.headers["Content-Type"] = "text/html; charset=utf-8"
    return resp

Note the important distinction from Modules 04 and 05: in a body-context injection, a payload like <script>alert(1)</script> contains angle brackets that HTML encoding would neutralise. In an href-context injection, the payload javascript:alert(1) contains no characters that require HTML encoding. The colon, letters, and parentheses are all valid unencoded characters. HTML encoding as a universal defence fails here entirely.

Warm-up

Exercise 1 — Why HTML Encoding Fails for href

Open the Console on the /link-preview page after firing a javascript: payload. Now try the same endpoint with ?url=<img src=x onerror=alert(1)>. What happens? Does the tag injection fire or does HTML encoding stop it?

Then explain in writing: for the javascript:alert(1) payload, which characters in the payload would be affected by HTML encoding (&, <, >, ", ')? Why does HTML encoding not protect href against this specific payload?

Warm-up

Exercise 2 — The Open Redirect in Burp

Configure your browser to proxy through Burp Suite. Navigate to: 

/redirect?url=javascript:alert(document.domain)

In Burp Proxy → HTTP history, find the request. Examine the response:

  • What HTTP status code is returned?
  • What is the exact value of the Location response header?
  • Forward the request. What happens in the browser?

Now try the same with a legitimate redirect: ?url=/. Compare the two Location headers. What is the minimum validation that would block the javascript: case without breaking the legitimate relative-URL case?

Core

Exercise 3 — Add Scheme Validation to /link-preview

Add a fixed version of /link-preview as a new route /link-preview-safe in both servers. The endpoint should:

  • Accept only URLs that start with http:// or https:// or /
  • For any other scheme, replace the URL with the string #blocked and log the rejected value
  • Still correctly render http://example.com as a clickable link

Test all of these inputs and document which pass and which are blocked: javascript:alert(1), JAVASCRIPT:alert(1), javascript:alert(1), https://example.com, /relative/path, data:text/html,<h1>hi</h1>.

Hint: Parse the URL first using Python's urllib.parse.urlparse() or JavaScript's new URL(url, location.href) — do not do string comparison on the raw input directly.

Core

Exercise 4 — Exfiltration via javascript: href

Build a realistic exfiltration payload for the /link-preview endpoint. The payload should:

  • Execute when the victim clicks the rendered link
  • Send document.cookie as a query parameter to /ping
  • Return the victim to the original page (no visible navigation away)

The void() operator is your friend for the last requirement. Test it: verify in DevTools → Network that the /ping?c=... request fires when you click the link.

Stretch

Exercise 5 — Stored URI Injection via Profile

This exercise simulates a stored URI injection scenario. The /profile page accepts a site= parameter that is placed in an href. In a real application, this value would be stored in a database when the user saves their profile.

Build a stored-style attack chain:

  • Construct a profile URL with site=javascript:fetch('/ping?stolen='+btoa(document.cookie))
  • Verify the fetch fires when the Website link is clicked
  • Check /ping response confirms receipt
  • Then explain: how does this attack model differ in terms of attacker effort from the reflected version in Step 2? When would the stored version be the preferred attack vector?

As a bonus: research whether btoa() will correctly encode all possible cookie values. What characters in a cookie could break the base64 encoding, and what is the correct alternative?

What's Next

Module 07 — Tag & Namespace Confusion (SVG, MathML, iframe)

Modules 04–06 covered the three most common execution mechanisms in HTML body, event handlers, and URI contexts. Module 07 goes deeper into the parser itself: the HTML5 spec defines three parsing namespaces — HTML, SVG, and MathML — and the transitions between them are exploitable. Injecting a payload inside an SVG context gives it different parsing rules than the same payload in HTML context. A sanitiser that handles HTML correctly may mis-handle an SVG fragment. This is the foundation for understanding Mutation XSS (Module 13), which exploits the differential between what a sanitiser parses and what the browser re-parses after sanitisation.
