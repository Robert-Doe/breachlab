Module 13 — Mutation XSS (mXSS)

XSS Mastery Course · PhD-Level Cybersecurity · Prerequisite: Modules 01–12

1. The mXSS problem: two parses, two results

Every sanitiser-based XSS defence is built on a shared assumption: the sanitiser and the browser parse HTML the same way. Mutation XSS (mXSS) is the class of attacks that breaks this assumption.

mXSS was first formally documented by Mario Heiderich et al. in "mXSS Attacks: Attacking well-secured Web-Applications by using innerHTML Mutations" (CCS 2013). The core observation: the HTML5 parser is context-dependent — the same string produces different DOM trees depending on the parsing context (namespace, parent element, scripting state). A sanitiser that models one context and produces output that is re-parsed in a different context may produce a different — and dangerous — result.

Formal definition: Given a sanitiser S and an attacker-controlled string X, if S(X) = Y (sanitised, "safe"), but innerHTML(Y) = Z where Z contains executable content, then the system is vulnerable to mXSS. The attack exploits the gap between how S parses Y and how the browser's innerHTML re-parses Y.

2. HTML5 parsing is not a pure function

The HTML5 parsing algorithm is defined in terms of a state machine that consumes a byte stream. Critically, the parser's behaviour depends on its current state, which is affected by:

  • The current namespace: HTML, SVG, or MathML. Different elements are defined in each namespace. An element that is a text container in one namespace may be a structured element in another.
  • The parent element: Table, select, textarea, and other elements have special child content models. Content not conforming to the model is handled by specific error-recovery rules.
  • The scripting flag: Whether scripting is enabled or disabled changes how <noscript>, <template>, and some other elements are parsed.
  • The insertion mode: "in table", "in row", "in cell", "in caption", "in foreign content" — each mode has different error recovery behaviours.

A sanitiser that does not perfectly model all of these states and their interactions will produce output that the browser re-parses differently.

3. Foster parenting — the table mutation

The HTML5 specification defines "foster parenting" as the error-recovery rule for content that is not valid inside a <table> element. Valid table content is limited to <caption>, <colgroup>, <tbody>, <tfoot>, <thead>, and whitespace/comments. Anything else triggers foster parenting.

When the parser encounters disallowed content inside a table, it does not reject it — it moves the content to just before the table in the current parent context. This is why it is called "foster parenting": the table's parent element adopts the misplaced content.

Input HTML:   <table><img src=x onerror=alert(1)></table>

Parser insertion mode: "in table"
Parser encounters <img> — not valid table content
Foster parenting: img is inserted before the table in the parent

Resulting DOM:
  BODY
  ├── IMG (onerror=alert(1)) ← moved here by foster parenting
  └── TABLE (empty)

The sanitiser that accepted <table><img src=x onerror=alert(1)></table> as "contained" was modelling the HTML wrong. The img is not contained — it escapes the table and lands in the body.

Why sanitisers miss this: A regex-based or tree-based sanitiser that does not simulate the HTML5 table error-recovery rules will see <img> inside <table> and accept it because it does not model the parser moving it outside.

4. Namespace boundary mutations

4.1 SVG style as CDATA

In the SVG namespace, <style> and <script> elements are defined as containing raw text (CDATA). The parser does not look for child elements inside them — everything until the closing tag is treated as character data. In the HTML namespace, <style> also contains raw text, but the closing delimiter rules differ subtly across parsing states.

The classic mXSS attack exploiting this:

Payload: <svg><style><a id="</style><img src=x onerror=alert(1)>">

SVG parser perspective:
  <style> content = CDATA = everything until </style>
  Content: <a id="</style><img src=x onerror=alert(1)>">
  This is raw text. Nothing executes.

Serialised (innerHTML readback):
  <svg><style><a id="</style><img src=x onerror=alert(1)>"></style></svg>

Re-inserted into HTML via innerHTML:
  Parser sees <style>...</style> — raw text until FIRST </style>
  Style content: <a id="
  Then: <img src=x onerror=alert(1)> — this is HTML markup!
  onerror fires.

4.2 MathML annotation-xml namespace switch

The MathML <annotation-xml> element with encoding="text/html" or encoding="application/xhtml+xml" triggers a namespace switch back to the HTML namespace. Content inside becomes HTML, not MathML. A sanitiser that does not model this transition may allow HTML content inside MathML that it believes is inert MathML text.

<math>
  <annotation-xml encoding="text/html">
    <img src=x onerror=alert(1)>   ← HTML namespace here
  </annotation-xml>
</math>

5. <noscript> — scripting state duality

The HTML5 specification defines two parsing modes for <noscript>:

  • Scripting enabled: <noscript> content is treated as raw text — the parser does not look for HTML tags inside it. The content is a raw string until </noscript>.
  • Scripting disabled: <noscript> content is parsed as full HTML — tags inside are parsed and rendered normally (because noscript's fallback content needs to be rendered).

A sanitiser library that is invoked with scripting disabled (as many server-side HTML parsers are, since they have no JS runtime) sees noscript content as HTML and sanitises it according to HTML rules. When the sanitised output is served to a browser with scripting enabled, the browser treats the noscript content as raw text — meaning the sanitiser's HTML-parse model was wrong for the target environment.

Payload: <noscript><p title="</noscript><img src=x onerror=alert(1)>">

Sanitiser (scripting off — sees noscript as HTML):
  Parses: <p title="...> — a p element with a title attribute
  The attribute value contains characters the sanitiser may pass as safe text.
  Output: <noscript><p title="</noscript><img src=x onerror=alert(1)>"></noscript>

Browser (scripting on — noscript = raw text):
  Raw text content of noscript: <p title="
  </noscript> terminates the raw text region.
  Remaining: <img src=x onerror=alert(1)>" — parsed as HTML.
  onerror fires.

6. <template> — inert activation

The <template> element was introduced in HTML5 as a mechanism for holding inert, reusable HTML fragments. Its content is parsed into a separate document fragment — a subtree that is not part of the main document. Scripts, stylesheets, and event handlers in a template fragment do not execute and are not rendered.

The mXSS risk arises when application code clones and activates a template that was populated with user-supplied content:

// Common pattern in web frameworks:
const tmpl = document.querySelector('#user-template');
tmpl.innerHTML = userContent;       // user content loaded into template
// ... sanitiser may not run, or may see inert context ...
document.body.appendChild(tmpl.content.cloneNode(true));  // activation!

If the sanitiser evaluated the template content while it was inert (no execution) and passed it, the cloneNode activation later makes the payload live.

7. DOMPurify's historical mXSS vulnerabilities

DOMPurify is the gold-standard client-side sanitiser, but it has been affected by multiple mXSS bypasses — each discovered as a new parser edge case was identified:

CVE / IDYearMechanismFix
DOMPurify < 1.0.112015SVG style CDATA namespace confusionNamespace-aware serialisation
DOMPurify < 2.0.12019MathML annotation-xml namespace switchAllowlist annotation-xml encodings
DOMPurify < 2.0.172020noscript scripting-state confusionTreat noscript as opaque in all states
DOMPurify < 3.0.62023Template element activation bypassSanitise template content explicitly
DOMPurify < 3.1.32024Foster parenting in new browser versionsTwo-pass sanitisation validation
Lesson: Even the best-maintained sanitiser library has shipped mXSS vulnerabilities. This is not a criticism of DOMPurify — it is evidence that the HTML5 parsing specification is complex enough that no implementation has yet captured it perfectly. Always use the latest version of DOMPurify and treat any sanitiser as potentially bypassable until proven otherwise in your threat model.

8. Implications for your intervention

mXSS directly constrains what your PhD intervention can claim to prevent:

  • If your intervention operates at the sanitiser layer: it is subject to all mXSS bypass classes described here. Your threat model must acknowledge this and either (a) use a two-pass fixed-point sanitiser, or (b) add a layer above sanitisation (Trusted Types, CSP) that prevents innerHTML use entirely.
  • If your intervention operates at the DOM sink layer (Trusted Types): mXSS is significantly reduced because the insertion point itself is gated — all innerHTML assignments must go through a trusted type policy that can apply context-aware sanitisation at the actual insertion context, not in a detached tree.
  • If your intervention is a static analysis tool: it must model all mXSS-relevant parse contexts (table, namespace switches, noscript, template) to avoid false negatives.
The two-pass invariant: A sanitiser is mXSS-resistant if and only if applying it twice to the same input produces identical output: S(S(X)) = S(X) for all X. If a second pass changes the output, the sanitiser's parse model diverges from the browser's — the gap is exploitable.
