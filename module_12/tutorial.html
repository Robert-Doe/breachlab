Module 12 — Filter Evasion & Obfuscation

XSS Mastery Course · PhD-Level Cybersecurity · Prerequisite: Modules 01–11

1. Why filters fail: the fundamental problem

Server-side input filters that attempt to block XSS operate on text — they inspect the raw string value and look for patterns that resemble attack payloads. This is structurally inadequate for three reasons:

  1. The context is not known at filter time. A filter cannot know whether the value will end up in an HTML attribute, a script string, a CSS property, or a JavaScript event handler — each requires different encoding and has different attack surface.
  2. The parser runs after the filter. Browsers decode HTML entities, URL-encoding, and Unicode escapes after the server sends the response. A filter that blocks < but not &lt; has a bypass built in.
  3. The attack surface is too large to enumerate. HTML5 defines 170+ event handler attributes. JavaScript provides hundreds of ways to invoke a function. No blocklist can enumerate them all.
The core insight: The only correct defence against injection is context-aware output encoding or allowlist-based sanitisation — not blocklists, stripping, or content inspection. Filters are a false defence. Understanding how they fail is essential for threat modelling: any filter-based defence in a system under review should be treated as no defence.

2. Blocklist bypass taxonomy

2.1 Synonym substitution

A filter blocking alert is bypassed with confirm(), prompt(), console.log(), or — for execution proof without a dialog — any side-effecting JS expression.

A filter blocking specific event handlers (onerror, onload) is bypassed with the 160+ other handlers. Key handlers not on typical blocklists:

2.2 Case variation

HTML attribute names are case-insensitive in the HTML parser. onerror, ONERROR, oNeRrOr, OnErRoR are all equivalent. A case-sensitive blocklist fails immediately.

<img src=x OnErRoR=alert(1)>

2.3 Whitespace and delimiter variation

HTML parsers accept a wide range of whitespace between tag components. These are all valid:

<img src=x onerror=alert(1)>          <!-- standard -->
<img src=x	onerror=alert(1)>         <!-- tab -->
<img/src=x/onerror=alert(1)>         <!-- slash separator -->
<img src=x
onerror=alert(1)>                     <!-- newline -->

2.4 Non-script vectors

Filters targeting <script> tags miss every other XSS vector. As demonstrated throughout this course, SVG, MathML, <img>, <details>, <input>, <video>, <audio>, and <body> all carry event handlers.

3. Tag stripping failure modes

3.1 Single-pass non-recursive stripping

A regex that strips <script>…</script> in one pass is defeated by nested tags that reconstruct the target after stripping:

Input:   <scr<script>ipt>alert(1)</scr</script>ipt>
Regex removes <script> and </script>:
Output:  <script>alert(1)</script>

The attacker wraps the forbidden tag inside itself. When the regex removes the inner occurrence, the outer halves join to form the original forbidden tag.

3.2 Greedy vs. non-greedy matching

A greedy regex that matches from the first <script to the last </script> collapses all script blocks into one removal. A non-greedy regex that matches each pair individually can be defeated by the nested technique. Neither is correct — the HTML parser is not a regex machine.

3.3 MIME-type confusion

Some filters strip tags from JSON, XML, or plain-text responses but forget that the browser parses based on Content-Type, not URL extension. A response served as text/html is always parsed as HTML regardless of what the developer intended.

4. Encoding bypass mechanics

The HTML parser decodes character references before handing content to downstream processors. This creates a two-stage pipeline that filters operating in only one stage cannot fully observe:

Network (filter sees this) → HTML parser → DOM (browser executes this)

Filter sees:  &lt;img src=x onerror=alert(1)&gt;
HTML parser decodes: <img src=x onerror=alert(1)>
Browser executes the onerror event

4.3 URL encoding

URL-encoded input (%3Cscript%3E) is decoded by the server's URL parser before the filter runs — unless the filter operates on the raw encoded bytes. Filters on decoded values miss double-encoded inputs (%253C → URL-decoded to %3C → if decoded again, <).

5. WAF bypass methodology

A systematic WAF bypass approach mirrors fuzzing methodology:

  1. Probe the WAF's rules individually. Send inputs that test one rule at a time: raw script tag, encoded script tag, event handler, javascript: URI. Observe which are blocked and which pass.
  2. Map rule interactions. Test combinations: does the WAF's encoding normalisation happen before or after keyword matching? Does stripping happen before or after length checks?
  3. Find the bypass class. Is the WAF blocking by keyword, by regex, by tag whitelist/blacklist, or by heuristic score? Each has a different bypass class.
  4. Minimise the bypass payload. Once a bypass is found, reduce it to the shortest form that passes all rules. Shorter payloads also improve length-limit bypass.
Burp Suite workflow: Send the target input to Burp Intruder. Use the XSS payload list from Burp's built-in library (or a custom wordlist) as the payload set. Filter for responses that differ from the "blocked" template — these are your bypass candidates.

6. JavaScript obfuscation — the full taxonomy

Once a payload reaches JavaScript execution context, the attacker can obfuscate the JavaScript itself. These techniques are relevant when the application or WAF inspects JavaScript content (e.g., scanning event handler values).

6.1 Function call obfuscation

alert(1)                              // standard
window.alert(1)                       // property access
window['alert'](1)                    // bracket notation
window['al'+'ert'](1)                 // concatenated property name
this['alert'](1)                      // 'this' in global scope is window
self['alert'](1)                      // same
top['alert'](1)                       // same
alert`1`                              // tagged template literal — no parens
(alert)(1)                            // extra parens — parsed identically

6.2 eval-based obfuscation

eval('alert(1)')
eval(atob('YWxlcnQoMSk='))           // base64
eval('alert(1)')                 // unicode escape inside string
eval(String.fromCharCode(97,108,101,114,116,40,49,41))
Function('alert(1)')()               // Function constructor
setTimeout('alert(1)',0)             // string-form setTimeout
setInterval('alert(1)',1e9)          // string-form setInterval

6.3 Constructor chain (no eval keyword)

[]['constructor']['constructor']('alert(1)')()
// [].constructor === Array
// Array.constructor === Function
// Function('alert(1)')() executes alert(1)

6.4 JSFuck — 6-character alphabet

JSFuck encodes any JavaScript using only [ ] ( ) ! +. The output is valid JavaScript that evaluates to any desired expression via coercions and array/function manipulations. It is impractical in length-limited contexts but theoretically proves that no JS content filter can be complete.

7. Implications for your intervention (PhD context)

This module defines what your intervention must not rely on:

  • No blocklists. Any blocklist-based pre-processing step in your intervention has the bypass properties described above. If your intervention includes a filter, it must be an allowlist sanitiser (DOMPurify-style), not a blocklist.
  • No regex-based tag detection. The HTML context is not regular. Use an HTML parser (DOMParser, parse5, html5lib) to analyse structure, not string patterns.
  • Encoding must be context-aware. If your intervention outputs user data into a page, the encoding function must know the output context (HTML content, HTML attribute, JavaScript string, CSS value) and apply the correct escape sequence for that context.
  • WAF bypass means attacker-controlled. If your threat model assumes a WAF as a layer in the defence, model the WAF as bypassable. Your intervention should not depend on WAF-level filtering as a security guarantee.
What works: The only robust client-side XSS defences are (1) DOMPurify allowlist sanitisation applied at every rendering sink, (2) Content Security Policy configured to block inline execution, and (3) Trusted Types to enforce (1) at the platform level. Modules 17–18 cover these in depth.
