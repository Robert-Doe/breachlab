Event Handler Injection:
Mechanism 2 in Depth

Blocking <script> tags is the single most common "fix" applied to XSS reports in legacy codebases. This module systematically demonstrates why it fails — and introduces the 40+ event handlers that make Mechanism 2 the most versatile and durable XSS execution path available to attackers.

Concept 1 — Why Event Handlers Are the Primary XSS Vector

When security researchers report XSS vulnerabilities, developers typically patch the most obvious vector first — the <script> tag. A filter is added: strip <script>...</script>, close the ticket. The application remains vulnerable to every other execution mechanism because the developer conflated "XSS" with "script tag injection."

The HTML5 specification defines over 150 event handler attributes. Every single one of them executes JavaScript. They work on any HTML element — not just the "dangerous" ones. A <div>, a <p>, a <span> — all can carry event handlers. An allowlist-based sanitiser that permits "safe" tags but does not carefully filter their attributes is equally broken.

More critically: event handlers injected via innerHTML do execute, unlike <script> tags. This is the critical asymmetry that makes Mechanism 2 the dominant vector in DOM-based XSS. Every DOM XSS payload you will encounter from Module 09 onward uses event handlers rather than script tags, precisely because of the HTML5 innerHTML restriction.

Warning — innerHTML Is Not "Safe" Without Event-Handler Filtering The HTML5 spec says innerHTML does not execute <script> tags. This is not a security feature — it is a rendering optimisation. Event handlers on any element injected via innerHTML fire normally. textContent is the only DOM property that truly treats its argument as inert text. Use textContent for user-supplied strings that should appear as visible text. Use innerHTML only for trusted, sanitised HTML.

Concept 2 — The Zero-Interaction Events

The most dangerous event handlers are those that fire without any user action. They make XSS completely silent — the victim opens the page and the payload executes before they read a single word. The five most important zero-interaction events for XSS are:

onerror
Fires when a resource fails to load. src=x deliberately fails. Works on img, video, audio, object, input[type=image]. The single most reliable zero-interaction vector.
onload
Fires when an element finishes loading. <svg onload=...> fires immediately when the SVG is parsed, even inline. <body onload=...> fires when the full page loads.
ontoggle
Fires on <details> when its open state changes. The open attribute causes an immediate toggle at parse time — before any user interaction. Works via innerHTML.
onfocus
Fires when an element receives focus. Combined with autofocus, the browser focuses the element immediately on page load — zero user action required.
onanimationstart
Fires when a CSS animation begins. If a keyframe animation is applied to an element via an inline style attribute, it starts immediately. No user action, no external stylesheet needed.
PhD Insight — Zero-Interaction Events and Threat Severity The distinction between zero-interaction and interaction-required events is critical for threat model severity ratings. A zero-interaction XSS payload requires only that the victim's browser loads the page — the exploit is automatic. No phishing, no social engineering, no clicks. This maps to the highest severity ratings (CVSS 9.0+) for stored XSS vulnerabilities. An interaction-required payload (onmouseover, onclick) requires some level of social engineering — lower severity, but still exploitable in targeted attacks. When writing your threat model, the interaction requirement should be an explicit parameter of your attacker capability assumptions.

Concept 3 — Why Blocklists Always Fail

The fundamental problem with blocklist-based XSS filters is enumeration: the attacker only needs one vector the filter doesn't cover; the filter must cover all of them. This asymmetry is structurally unwinnable for the defender operating at the string/keyword level.

Consider the progression of a typical legacy application's XSS filter history:

Bug report #Payload usedFix appliedStill bypassed by
1<script>alert(1)</script>Strip <script><img src=x onerror=...>
2<img onerror=...>Strip onerror<svg onload=...>
3<svg onload=...>Strip onload<details ontoggle=...>
4<details ontoggle=...>Strip ontoggle<input autofocus onfocus=...>
5<input onfocus=...>Strip onfocusonanimationstart, onpointerover, …

Each fix patches one vector and leaves 145+ others intact. The correct fix — applied after report #1 — is to replace the blocklist with an allowlist sanitiser that permits only specific known-safe tags and attributes. We study allowlist sanitisers in Module 17 and their bypass (mXSS) in Module 13.

Concept 4 — The Event Handler on Any Element

HTML5 global event attributes can be applied to any HTML element. This means that even a sanitiser which correctly allowlists only "safe" tags like <div>, <p>, <span>, <em>, and <strong> is still vulnerable if it permits any event handler attributes on those tags. 

// "Safe" tag with dangerous attribute — both would pass a tag-only allowlist
<p onmouseover="alert(document.domain)">hover me</p>
<em onclick="alert(1)">click me</em>
<strong onfocus="alert(1)" tabindex="1">focus me</strong>

An allowlist sanitiser must therefore maintain two separate allowlists: permitted tags AND permitted attributes (per tag or globally). DOMPurify's default configuration allowlists approximately 85 tags and 80 attributes — none of which are event handler attributes. This is the correct approach. Any configuration that permits on* attributes is insecure.

Code Walkthrough — /vuln-display (Flask)

lab_server.py — /vuln-display
import re

@app.route("/vuln-display")
def vuln_display():
    content = request.args.get("content", "")

    # THE "SANITISER": one regex, strips <script> blocks only.
    # re.IGNORECASE handles <SCRIPT>, <Script>, <ScRiPt>.
    # [\s\S]*? is a non-greedy match for any content including newlines.
    #
    # What it misses (everything else):
    #   - Event handler attributes on ANY element
    #   - javascript: URIs in href/src/action
    #   - SVG/MathML with embedded event handlers
    #   - data: URIs in iframe/object/embed
    #   - CSS expression() (legacy IE)
    #   - All 150+ HTML event attributes
    filtered = re.sub(
        r'<script[\s\S]*?</script>',
        '',
        content,
        flags=re.IGNORECASE
    )

    # Both 'content' and 'filtered' are reflected into the page.
    # 'filtered' is placed inside a div that renders it as HTML.
    # Event handlers in 'filtered' will execute when their events fire.
    body = f"""
  <div class="box">
    <label>After removing <script> tags:</label>
    <pre>{filtered}</pre>
  </div>
  <div class="box">
    <label>Rendered (event handlers still active):</label>
    <div id="rendered">{filtered}</div>   <!-- still vulnerable -->
  </div>"""
    return make_response(page("Vuln Display", body),
                          200, {"Content-Type": "text/html; charset=utf-8"})
