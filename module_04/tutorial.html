Script Tag Injection:
Mechanism 1 in Depth

The oldest and most straightforward execution mechanism. The browser sees a <script> tag, hands its content to the JavaScript engine, and executes it immediately. Understanding this baseline precisely — when it works, when it doesn't, and why — is the foundation for everything that follows.

Prerequisites

Modules 01–03 complete. You know the five mechanisms and the four injection contexts. Burp Suite is installed and proxying Chrome.

What you will build in this module
  • Three vulnerable server endpoints: body, attribute, and script injection contexts
  • An interactive attack demo page (attack_01_script.html) with seven payload variants
  • Hands-on experience firing reflected XSS in all three contexts via Burp Suite
  • A mental model of the full reflected XSS attack chain — from URL to victim's browser

Concept 1 — What "Reflected" Means and Why It Matters

A reflected XSS vulnerability exists when a server takes a value from an HTTP request — a URL parameter, a form field, a header — and includes it verbatim in the HTML response without encoding it. The payload is reflected: the server sends back what you gave it, as part of the page. The browser then parses that page, encounters the injected code, and executes it.

The attack chain has five steps. Every one of them matters for threat modelling, because each step is a potential intervention point:

1. CraftAttacker builds malicious URL with payload in parameter
→
2. DeliverVictim receives URL (email, chat, QR code, shortened link)
→
3. RequestVictim's browser sends GET request to target server
→
4. ReflectServer embeds payload in HTML response without encoding
→
5. ExecuteBrowser parses response, script runs in victim's session

Notice that the attacker never has to compromise the server. The server is an unwilling participant that faithfully serves the attacker's payload back to the victim. The victim's browser executes it because it came from the trusted server's origin. This is why Same-Origin Policy, the browser's primary access control mechanism, provides no protection — the code is on the right origin. It was put there by the attacker, but the browser can't know that.

PhD Insight — Reflected XSS Is Still Ubiquitous Despite being the oldest and most well-understood XSS class, reflected XSS consistently appears in bug bounty programmes and CVE reports. The reason is structural: every web application has search boxes, error pages, redirect parameters, and form prefills — all of which reflect user input. A single missed encoding call anywhere in a large codebase creates a vulnerability. The 2021 OWASP Top 10 places injection (which includes XSS) at #3. The volume of reflected XSS in the wild motivates your research question: existing defences are clearly insufficient for real-world adoption at scale.

Concept 2 — The Three Injection Contexts for Script Execution

Script-tag injection always begins with identifying the injection context — where in the HTML document your input lands. Each context requires a different technique to reach executable code.

Body Context: Direct Tag Injection

The attacker's input appears directly in the document body: <p>Results for: [INPUT]</p>. A < character here starts a new tag immediately. The simplest possible injection is a complete script tag: <script>alert(1)</script>. No preamble, no escaping, no setup. The browser sees the opening script tag, reads until the closing tag, and hands the content to the JS engine.

Variations: the script tag can load a remote file (src=), use upper-case (<SCRIPT>), or be preceded by a closing tag that escapes a different context (</title>, </style>).

Script Context: Breaking Out of a JS String

The attacker's input is embedded inside a <script> block as a string literal: var q = "[INPUT]";. The attacker cannot inject a new <script> tag here — they are already inside one. Instead, there are two escape routes:

  • String break: inject a " to close the string, then arbitrary JS, then // to comment out the rest: "; alert(1);//
  • Tag break: inject </script> — the HTML parser closes the script block immediately even if the JS tokeniser is in the middle of a string literal. The browser parses HTML before parsing JS.

Attribute Context: Breaking Into the Tag Body

The attacker's input is inside a quoted HTML attribute: <input value="[INPUT]">. Injecting " closes the attribute, and the attacker is now in the tag body, where they can add event handlers. The trailing part of the original attribute becomes an attribute of its own (absorbed by x="): 

// Template:       <input value="[INPUT]">
// Injected value: " onmouseover="alert(1)" x="
// Result:         <input value="" onmouseover="alert(1)" x="">
Tip — Always Identify Context Before Choosing Payload The single most common mistake made by developers trying to fix XSS is applying the wrong type of encoding for the context. HTML-encoding < and > stops body-context injection but does nothing to prevent attribute-context injection (the attacker uses ", not <). Script-context injection requires JavaScript-aware encoding, not HTML encoding. The three endpoints in this module let you experience each context independently — this trains the instinct to identify context before acting.

Concept 3 — The innerHTML Exception: A Critical Constraint

When you assign a string containing a <script> tag to element.innerHTML, the script tag is parsed into a DOM element but not executed. This is mandated by the HTML5 specification (Section 8.4.1): script elements created by the innerHTML setter are marked "already started" by the tree builder and the JS engine skips them.

This constraint is why DOM XSS (Module 09) uses event handlers injected via innerHTML, not script tags. <img src=x onerror=alert(1)> assigned via innerHTML does execute — the onerror handler is not subject to the same restriction. This asymmetry is important to understand: when evaluating a DOM XSS sink, the question is not "can a script tag execute here?" but "can an event handler execute here?" The answer is almost always yes for any HTML-parsing sink.

Warning — The innerHTML Exception Creates False Confidence Developers who discover that el.innerHTML = userInput doesn't execute script tags sometimes conclude that it is therefore safe. It is not. Event handlers, onload on images, onerror on broken resources, javascript: URIs in href attributes — all execute via innerHTML. The only safe DOM property for displaying arbitrary text is textContent, which never parses HTML.

Concept 4 — Reading HTTP Responses with Burp Suite

Burp Suite's Repeater tool is the most important instrument for studying reflected XSS. It lets you modify a request and immediately see the raw HTTP response — the exact bytes the server sent before the browser parses them. This is crucial because:

  • The browser's DevTools Elements panel shows you the parsed DOM, not the raw HTML. They differ.
  • Burp shows you exactly where your input landed in the response and what surrounds it.
  • You can test dozens of payload variations in seconds without writing URLs by hand.
  • The response headers are visible — CSP, X-Content-Type-Options, Set-Cookie flags — telling you what defences exist.

The workflow: navigate to a target URL in Chrome with Burp proxying → find the request in Burp's HTTP History → right-click → Send to Repeater → modify the payload in the request → Send → inspect the response. This is the workflow used for every module from here onward.

Code Walkthrough — lab_server.py /search

lab_server.py — /search route
@app.route("/search")
def search():
    # request.args.get() reads the URL query string.
    # ?q=hello  →  q = "hello"
    # ?q=<script>alert(1)</script>  →  q = "<script>alert(1)</script>"
    # Flask does NOT decode HTML entities — the value is the raw URL-decoded string.
    q = request.args.get("q", "")

    # THE VULNERABILITY: q is f-string interpolated directly into HTML.
    #
    # The safe alternative is one of:
    #   import html; html.escape(q)          ← HTML-encode for body context
    #   flask.escape(q)                      ← same, Flask helper
    #   use render_template() with Jinja2    ← auto-escapes by default
    #
    # We deliberately avoid all of these so payloads execute.
    body = f"""
  <div class="box">
    <label>Results for:</label>
    <div id="query-echo">{q}</div>   <!-- INJECTION POINT -->
  </div>"""

    resp = make_response(page_shell("Search", body))
    resp.headers["Content-Type"] = "text/html; charset=utf-8"
    # No CSP, no X-XSS-Protection — bare, undefended endpoint.
    # Module 17 adds these headers to the SAFE versions of these routes.
    return resp
lab_server.py — /search-js route (script context)
@app.route("/search-js")
def search_js():
    q = request.args.get("q", "")

    # The injected value lands inside a JS string literal.
    # To safely embed user data in a JS context, use json.dumps():
    #   import json
    #   safe_q = json.dumps(q)   # adds quotes + escapes " \ and </
    # We skip this to preserve the vulnerability.
    body = f"""
  <script>
    var searchQuery = "{q}";    // <-- INJECTION POINT
    document.getElementById('result').textContent =
      'You searched for: ' + searchQuery;
  </script>"""
    return make_response(page_shell("Search JS", body),
                          200, {"Content-Type": "text/html; charset=utf-8"})

Core

Exercise 3 — Fix the Vulnerability

In lab_server.py, create a new safe route /search-safe that does the same thing as /search but correctly encodes output for the body context. In Python: 

import html
safe_q = html.escape(q)   # converts < → &lt;  " → &quot;  etc.

Do the same in lab_server.js: 

function escapeHtml(str) {
  return str
    .replace(/&/g, '&amp;')
    .replace(/</g, '&lt;')
    .replace(/>/g, '&gt;')
    .replace(/"/g, '&quot;')
    .replace(/'/g, '&#x27;');
}

Navigate to /search-safe?q=<script>alert(1)</script>. Verify the script tag is displayed as literal text, not executed. Then View Source — what do you see where the payload was? Use the Elements panel — how does the browser represent the encoded characters in the DOM?

Core

Exercise 4 — Fix the Script Context

Create a safe /search-js-safe route that correctly handles user data embedded in a JavaScript context. The correct fix is json.dumps() in Python or JSON.stringify() in Node — these escape the characters that are dangerous in a JS string context (", \, and the </ sequence that closes a script block): 

# Python
import json
safe_q = json.dumps(q)   # "hello"  →  '"hello"'
                           # </script>  →  '"<\\/script>"' (/ escaped)

// Node.js
const safe_q = JSON.stringify(q);
// Then use in template: var searchQuery = ${safe_q};
// Note: JSON.stringify adds its own quotes, so don't add extra quotes in the template

Test with ?q=";alert(1);// — the alert should not fire. Then test with a normal query like ?q=hello world — it should still display correctly.
