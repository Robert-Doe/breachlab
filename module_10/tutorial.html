Module 10 of 19

Stored XSS
& Second-Order Attacks

Reflected and DOM-based XSS require the attacker to deliver a URL to the victim. Stored XSS eliminates that requirement: the payload executes automatically for every subsequent visitor, forever — or until someone notices and removes it. Second-order attacks extend this by storing the payload in one context and detonating it in a different, more privileged one.

Prerequisites

Modules 01–09 complete. You have fired reflected and DOM-based XSS across every execution mechanism. This module adds the persistence layer.

What you will build in this module
  • A comment board (/board) with POST storage and raw rendering
  • An admin panel (/admin) that renders stored profiles — second-order context
  • A profile registration form (/admin/profile) — public attacker entry point
  • A 5-step attack demo covering stored XSS, author-field injection, second-order escalation, and XSS→CSRF chaining

Concept 1 — The Storage Model

In reflected XSS, the payload travels in the HTTP request and immediately returns in the response. The attack window is a single request/response cycle — the victim must be induced to send the crafted request.

In stored XSS, the payload is written to persistent storage (database, file, cache) in one request. All subsequent responses that include that stored data carry the payload. The attacker's interaction with the application ends at submission; the victim is anyone who later loads the affected page.

PropertyReflected XSSStored XSS
Delivery mechanismAttacker sends URL to victimVictim visits any page that shows stored data
Victims per payloadOne (per sent link)All visitors during dwell period
Server log visibilityPayload visible in access logPayload in storage; access log shows normal GET
CSRF token bypassRequires token theft in same requestCan exfil token in separate same-origin request
PersistenceNone — payload gone after responseDwell time = until manually removed
Typical CVSS score6–88–10

Concept 2 — Second-Order (Persistent Blind) XSS

Second-order XSS (also called "persistent blind XSS" in the blind XSS literature) occurs when the storage context and the execution context are different pages or application features. The key characteristic: the payload does not execute when submitted. The submitter cannot immediately confirm the injection worked. Execution happens later, in a context the attacker may not even be able to visit directly.

This module's admin panel models the most common second-order pattern:

  • Storage context: Public profile registration form — low privilege, no auth
  • Execution context: Admin user management panel — high privilege, admin auth
  • Time gap: Hours or days between submission and admin review
  • Attacker visibility: Attacker cannot see admin panel to confirm the payload — hence "blind"
PhD Insight — Second-Order XSS in Security Audits Second-order XSS is the most commonly missed XSS class in penetration tests and automated scans. Scanners that test only for immediate reflection will not detect it. A test that submits a payload to a registration form and checks only the registration confirmation page for reflection will miss execution in the admin panel entirely. The correct technique is to submit payloads with out-of-band callbacks (a payload that POSTs to a server you control) and wait for execution. This is the basis of blind XSS tools like XSS Hunter. When writing your PhD threat model, second-order XSS must be listed as a distinct threat with its own detection requirements.

Concept 3 — Stored XSS Enables CSRF Token Theft

A common developer misconception is that CSRF tokens protect against XSS-enabled CSRF. They do not. A stored XSS payload running in a victim's browser has full same-origin access. It can:

  1. Fetch any same-origin page that contains a CSRF token
  2. Parse the token from the response HTML
  3. Include the token in a forged POST request
  4. Exfiltrate the result
// XSS payload that steals CSRF token and uses it:
fetch('/settings')                        // 1. fetch page with CSRF token
  .then(r => r.text())
  .then(html => {
    const m = html.match(/csrf_token" value="([^"]+)"/);
    const token = m && m[1];              // 2. extract token
    return fetch('/settings/email', {
      method: 'POST',
      body: `email=attacker@evil.com&csrf_token=${token}`,
      headers: { 'Content-Type': 'application/x-www-form-urlencoded' },
      credentials: 'include'                // 3. send with victim's cookies
    });
  });                                       // 4. email changed to attacker's

This is why the OWASP Top 10 lists XSS as a prerequisite threat to CSRF: an application with stored XSS has effectively no CSRF protection for any page the victim's browser visits while the payload is active.

Exercises

Warm-up

Exercise 1 — Confirm Multi-Victim Behaviour

Submit a payload to the comment board that changes the page's background color to red when it fires (document.body.style.background='red'). Then open the board in three different browser tabs simultaneously. Confirm the payload fires in all three — each tab is a separate "victim".

Then open an incognito window (or a different browser entirely) and visit the board. Confirm the payload fires there too. Document: how many times did the payload fire in total? What does this tell you about the impact multiplier of stored vs reflected XSS?

Warm-up

Exercise 2 — Intercept POST in Burp

Configure Burp to intercept POST requests. Submit a comment and intercept the POST /board/post request. In Burp's Intercept tab:

  • Identify the two fields in the POST body
  • Modify the text field to contain <img src=x onerror=alert('via burp')>
  • Forward the modified request
  • Verify the modified payload is stored and executes on the board

This demonstrates that client-side form validation (if any) is bypassed by intercepting at the network level.

Core

Exercise 3 — CSRF Token Exfiltration Chain

This lab doesn't have CSRF tokens, but you can simulate the exfiltration chain. Add a hidden CSRF token to the comment board form in lab_server.py: 

# In board() function, add to the form:
import secrets
csrf = secrets.token_hex(16)
# Store in session (or just embed directly for demo):
# <input type="hidden" name="csrf_token" value="{csrf}">

Then build a stored XSS payload that:

  • Fetches /board
  • Extracts the CSRF token from the response HTML using a regex
  • Sends the token value to /ping?csrf=<token>

After submitting the payload, visit /board to trigger it, and verify the CSRF token appears in DevTools → Network under the /ping request.

Core

Exercise 4 — Threat Model Entry for Stored XSS

Write a formal threat model entry for the stored XSS vulnerability in the comment board, using the STRIDE framework:

  • Spoofing: How can stored XSS enable identity spoofing?
  • Tampering: What data can be modified via stored XSS in this application?
  • Repudiation: Can stored XSS be used to manipulate audit logs?
  • Information Disclosure: What data can be exfiltrated?
  • Denial of Service: Can stored XSS cause DoS?
  • Elevation of Privilege: How does the second-order attack in /admin achieve privilege elevation?

Include a severity rating (CVSS 3.1 base score) with justification. This entry should be suitable for inclusion in your PhD thesis threat model chapter.

Stretch

Exercise 5 — Out-of-Band Blind XSS Detection

The second-order profile attack is "blind" — the attacker cannot see the admin panel to confirm execution. Real blind XSS attacks use out-of-band callbacks. Simulate this:

  • Modify the profile payload to fetch /ping?blind=1&ua= + navigator.userAgent
  • Submit the profile at /admin/profile
  • Without visiting /admin yourself, have a classmate (or a second browser session) visit /admin
  • Monitor /ping requests in the first session's DevTools → Network
  • When your classmate loads /admin, you should see the /ping?blind=1 request appear — confirming blind XSS execution without the attacker ever loading the execution page

Research XSS Hunter (the blind XSS SaaS tool). Explain how it implements this callback pattern at scale, and what additional information it collects beyond the User-Agent.
