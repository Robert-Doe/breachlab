Attack 06 — Stored XSS & Second-Order Attacks

Payloads that persist across requests, executing for every subsequent visitor — and second-order injection where storage and execution contexts differ.

1
Basic Stored XSS — Comment Board
STORED EVERY VISITOR

Post a comment to the board with a zero-interaction payload. The payload will execute for every user who visits the board — including opening it in a fresh incognito window to simulate a different victim.

1
Attacker posts comment with onerror payload
2
Server stores raw HTML in memory (no sanitisation)
3
Any visitor to /board receives the payload in the page HTML
4
onerror fires in victim's browser — cookie exfiltrated
Name: Attacker Comment: <img src=x onerror="fetch('/ping?stolen='+btoa(document.cookie))">
Open Comment Board

Submit the payload via the form. Then open the board in a new incognito window to simulate a different victim visiting — the payload executes again. Check DevTools → Network for the /ping request.

2
Author Field Injection — Persistent Identity Hijack
STORED

Both the author name and the comment text are reflected raw. A payload in the author name executes on every comment card render — not just once per page load, but once per comment from that author. Store a zero-interaction payload in the author field with an innocuous-looking text.

Name: <img src=x onerror=alert('author field XSS: '+document.domain)> Comment: Great post!
Open Comment Board

If this author posts multiple comments, the payload fires once per card rendered. Submit 3 comments from this author and observe how many times alert fires on page load.

3
Second-Order Attack — Profile → Admin Panel
SECOND ORDER PRIVILEGE ESCALATION

The profile registration page (/admin/profile) is public-facing and appears harmless. However, stored profile data is rendered in the admin panel (/admin) without sanitisation. An attacker who registers a malicious profile can execute JavaScript in the admin's browser — achieving privilege escalation from a public user to code execution in an admin session.

1
Attacker visits public /admin/profile form — no auth required
2
Submits payload in the bio or website field
3
Admin navigates to /admin to review profiles
4
Payload executes in admin's browser — admin session cookie exfiltrated
5
Attacker uses stolen admin session to perform privileged actions
Username: attacker Bio: Researcher <img src=x onerror="fetch('/ping?admin_cookie='+btoa(document.cookie))"> Website: https://example.com
Open Profile Form Open Admin Panel

Submit the payload via the profile form, then open the admin panel. The admin panel's /ping request should appear with the cookie value.

4
Stored XSS → CSRF: Admin Action Without Credentials
CHAINED ATTACK

XSS in an admin panel can be used to perform CSRF — making authenticated requests as the admin without knowing the admin's password. The stored payload below, when executed in the admin's browser, sends a POST request to the clear endpoint (simulating a destructive admin action) and exfiltrates confirmation.

Bio: <img src=x onerror=" fetch('/board/clear', {method:'GET', credentials:'include'}) .then(()=>fetch('/ping?action=board_cleared')) ">
Submit XSS→CSRF payload Trigger in Admin Panel Reset Board
5
Dwell Time: Payload Persists Across Server Restarts
STORED

In this lab the store is in-memory (resets on restart). In a real application with a database, a stored XSS payload persists until:

  • A developer manually removes the malicious record
  • An automated scanner detects and removes it
  • The field is sanitised retroactively (rare — usually requires a migration)

This dwell time — potentially months or years — is what makes stored XSS the highest-impact XSS variant. A single payload can run in thousands of victim browsers before it's discovered. Research has documented stored XSS payloads active in production systems for 18+ months.
