Module 07 of 19

Tag & Namespace Confusion:
SVG, MathML, and iframe

The HTML5 parser is not a single-mode parser. It switches between three parsing namespaces — HTML, SVG, and MathML — as it encounters specific tags. Each namespace has different rules for what is valid, what executes, and what a "safe" tag means. Sanitisers that think in HTML namespace alone miss entire attack surfaces.

Concept 1 — Three Parsing Namespaces

The HTML5 specification defines a tree construction algorithm with a concept called adjusted current node. As the parser processes tokens, it tracks whether the current insertion point is in HTML, SVG, or MathML context. This context — the namespace — determines how subsequent tokens are parsed.

Three trigger elements switch the namespace:

Trigger elementSwitches toReverts on
<html> (root)HTML namespace (default)N/A
<svg>SVG namespace</svg> or integration points
<math>MathML namespace</math> or integration points

Namespace switches can be nested. A <foreignObject> inside SVG switches back to HTML. An <annotation-xml> inside MathML can contain SVG. These transitions create the "HTML integration points" and "MathML text integration points" defined in the spec — and exploited in mXSS.

PhD Insight — Namespace Confusion and Sanitiser Scope Most HTML sanitisers process the document in a single pass, treating it as an HTML document. When a sanitiser encounters an <svg> element it may allowlist it (SVG is legitimate in HTML5 content) without recognising that the content inside is parsed by different rules. A sanitiser that strips <script> from HTML context may not strip <script> from SVG context — or may strip it but leave intact the SVG-specific vectors like <animate> and <set>. This is the core mechanism behind many DOMPurify bypasses reported between 2019–2023, and the setup for Mutation XSS (Module 13).

Concept 2 — SVG Namespace Vectors

SVG is a full XML-based graphics format embedded in HTML5. It has its own element set, its own event model, and — critically — its own script execution model. The key differences from HTML that matter for XSS are:

  • Script execution in SVG context: A <script> tag inside <svg> in server-rendered HTML executes. The innerHTML restriction does not apply to server-rendered SVG.
  • onload on svg element: <svg onload=...> fires immediately on element parse — identical to <body onload=...> but injectable anywhere in the document.
  • SVG animation elements: <animate>, <set>, and <animateTransform> can mutate any attribute on target elements, including href, src, and event handler attributes.
  • foreignObject: Embeds a full HTML document inside SVG, parsed in HTML namespace. All HTML vectors work inside it.
  • use xlink:href: The SVG <use> element's href can reference a javascript: URI in some browsers.
// Zero-interaction SVG vectors — all fire without user action:

// 1. onload on svg tag
<svg onload="alert(document.domain)"></svg>

// 2. script inside svg (server-rendered only)
<svg><script>alert(1)</script></svg>

// 3. foreignObject with onerror
<svg><foreignObject><img src=x onerror="alert(1)"></foreignObject></svg>

// 4. animate mutating href to javascript: — fires on click
<svg><a><animate attributeName=href values=javascript:alert(1) /><text y=20>click</text></a></svg>

Concept 3 — MathML and HTML Integration Points

MathML is the third HTML5 parsing namespace. Most developers have never used MathML intentionally, which makes it an excellent injection surface — it's rarely in anyone's mental threat model and sanitiser test suites often skip it.

The critical element is <mtext>. In the HTML5 spec, <mtext> is a MathML text integration point — a location where the parser accepts HTML elements as children. Content inside <mtext> is parsed in HTML namespace, meaning:

  • An <img src=x onerror=...> inside <mtext> executes normally
  • Event handlers on HTML elements inside <mtext> fire normally
  • A sanitiser that only processes the MathML structure without recursing into mtext's HTML children will miss these vectors

The chain <math><mtext><table><mglyph><style> is the setup for several mXSS bypasses — the full mechanism is studied in Module 13. Here we focus on the simpler direct injection into mtext.

Concept 4 — iframe srcdoc and the sandbox Misconception

The srcdoc attribute specifies an inline HTML document for an iframe to render. Without a sandbox attribute, a srcdoc iframe inherits the parent's origin — scripts inside it can access parent.document.cookie, parent.localStorage, and the parent's full DOM.

The common developer response is to add sandbox. But the sandbox has flags, and combining the wrong flags negates the security:

sandbox valueScripts allowed?Same-origin?Risk
sandbox (empty)NoNo (unique origin)Low — scripts cannot run
allow-scriptsYesNo (unique origin)Medium — scripts run but isolated origin
allow-same-originNoYesLow — no scripts
allow-scripts allow-same-originYesYesCRITICAL — same as no sandbox
Warning — sandbox="allow-scripts allow-same-origin" Is Not a Mitigation The HTML5 spec explicitly states: "Setting both the allow-scripts and allow-same-origin keywords together when the embedded page has the same origin as the embedding page allows the embedded page to simply remove the sandbox attribute and then reload itself." An iframe with this combination is equivalent to no sandbox at all. Never use both flags together on user-supplied content.

Warm-up

Exercise 1 — Map the innerHTML Exception Precisely

Open the Console and run each of these snippets. Record: does each fire alert(1)? 

// A: script in HTML namespace via innerHTML
d1 = document.createElement("div");
d1.innerHTML = "<script>alert('A')<\/script>";
document.body.appendChild(d1);

// B: script inside svg via innerHTML
d2 = document.createElement("div");
d2.innerHTML = "<svg><script>alert('B')<\/script></svg>";
document.body.appendChild(d2);

// C: svg onload via innerHTML
d3 = document.createElement("div");
d3.innerHTML = "<svg onload=alert('C')></svg>";
document.body.appendChild(d3);

// D: foreignObject onerror via innerHTML
d4 = document.createElement("div");
d4.innerHTML = "<svg><foreignObject><img src=x onerror=alert('D')></foreignObject></svg>";
document.body.appendChild(d4);

Write down exactly which letter(s) fired. Look up the HTML5 spec section on "script elements" and the note about "already started" — find the exact sentence that explains why A and B don't fire via innerHTML but C and D do.

Exercise 4 — Safe iframe srcdoc

Add a /iframe-safe endpoint to both servers that renders user-supplied content in an iframe but prevents script execution and same-origin access. The correct configuration is: 

# Python — safe iframe
srcdoc = f'<html><body>{content}</body></html>'
# sandbox with NO allow-scripts and NO allow-same-origin
iframe = f'<iframe srcdoc="{srcdoc}" sandbox="allow-forms"></iframe>'

Test that /iframe-safe?q=<script>parent.document.title='HIJACKED'</script> does NOT change the parent's title. Then test that it also does not fire <img src=x onerror=alert(1)>. Document which sandbox flags you used and why.
