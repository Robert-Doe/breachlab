1. What a Threat Model Is (and Isn't)

A threat model is a structured enumeration of: what can go wrong, for whom, and what can be done about it. In XSS research, your threat model maps the attack taxonomy (M03–M14) against the existing defenses (M17) and explicitly names the gaps your research addresses.

A threat model that says "XSS is bad, defenses exist" is not a threat model — it is a summary. A PhD-level threat model is falsifiable: it makes specific claims about which attacks bypass which defenses under which conditions, and those claims are testable.

Framing for your PhD: Your intervention (novel defense, detection method, or analysis technique) should be positioned in the gap table below. The gap table is the "why this matters" for your committee. If your technique closes a row that is currently OPEN, you have a contribution.

3. Open Research Gaps (as of 2024–2025)

Gap 1 — mXSS: No Formal Model of Safe Round-Tripping

Mutation XSS arises because sanitizers and browsers model the HTML grammar differently. There is no formal, complete characterisation of the set of strings that are safe through all browser parsers. DOMPurify is empirically good but not provably complete. A formal grammar-theoretic model could enable provably safe sanitization.

Gap 2 — Prototype Pollution: Automated Gadget Discovery

Given a source (deepMerge) and a set of DOM sinks, no existing tool reliably finds all prototype pollution → DOM XSS chains in a real JavaScript codebase. The connection is through Object.prototype — invisible to taint analysis tools that track variables.

Gap 3 — DOM XSS in SPAs: Source Coverage

Existing DOM XSS detection tools (DOM Invader, etc.) work through dynamic analysis — they must exercise code paths to find taint flows. SPAs with route-dependent rendering have massive source coverage gaps. Techniques for complete static source enumeration in TypeScript/React SPAs are underdeveloped.

Gap 4 — Supply Chain: Runtime Integrity Enforcement

SRI is a build-time control. It doesn't handle dynamically loaded scripts, scripts loaded by third-party scripts, or runtime script mutation. A runtime integrity mechanism (analogous to memory integrity in OS security) for the browser script environment would address supply chain XSS at a different layer.

Gap 5 — CSP Bypass Landscape: Systematisation

Known CSP bypass techniques (JSONP gadgets, open redirectors in allowlisted hosts, base-uri manipulation) are catalogued ad hoc in blog posts and CTF writeups. A systematic study — given a CSP header, enumerate all remaining executable attack paths — is absent from the academic literature.

5. Evaluation Criteria for a Novel Defense

If your contribution is a defense, it must be evaluated along these axes:

  1. Coverage: Which attacks from the taxonomy does it stop? Test against M04–M14 plus your open gaps.
  2. Soundness: Does it produce false positives (blocking legitimate content)? Measured against a corpus of real-world rich HTML.
  3. Completeness: Does it miss attacks? Measured against a curated payload set (Module 19 is your starting corpus).
  4. Performance: What is the overhead? Sanitizers and TT policies add parse time. Acceptable thresholds depend on context.
  5. Deployability: Can it be adopted without breaking existing sites? Backward compatibility is the dominant reason defenses aren't adopted.
  6. Composability: Does it compose correctly with other defenses in the stack, or does it create gaps at the seams?
The deployability axis is underappreciated in academic defense papers. CSP adoption is low not because developers don't know about it, but because retrofitting it to existing codebases is expensive. A defense that is 95% as effective but requires zero migration effort will have 100× the real-world impact.
