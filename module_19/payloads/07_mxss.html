07 — Mutation XSS (mXSS)

10 payloads · Mechanism: Context-escape + reparse · Module reference: M13 · Lab: http://localhost:5000/mxss/innerHTML?q=PAYLOAD
How mXSS works: A sanitizer parses the input string and judges it safe. The sanitized string is then assigned to innerHTML. The browser re-parses it. Due to parser state differences (namespace context, foster parenting, raw-text mode), the second parse produces a different DOM — with an executable XSS payload. The sanitizer was correct about what it parsed. The browser parsed differently.
A. Table Foster Parenting
MXSSTABLE FOSTER
01
<table><td></td></table><img src=x onerror=alert(1)> <!-- Or via foster parenting: --> <table><img src=x onerror=alert(1)></table>
Contextimg tag injected inside table element — parser foster-parents it before the table Mechanism5 — Context escape: HTML5 parser ejects non-table content from table via foster parenting; ejected content is active HTML BypassesSanitizers that check the string and see <img> inside <table> (apparently contained), but after re-parse img is in body Stopped byDOMPurify; Trusted Types; sanitizers that simulate the browser's full parse NoteFoster parenting: when the HTML5 parser encounters non-table content inside a table, it "foster parents" it — moves it to just before the table element in the DOM. The content ends up in the document body as active HTML.
MXSSTABLE FOSTERSANITIZER BYPASS
02
<table><tbody></tbody><img src=x onerror=alert(1)></table>
Contextimg after tbody but inside table — only specific table-structure elements are valid inside table Mechanism5 — Foster parenting ejects img before table; onerror fires in document body BypassesString scanners; sanitizers that don't simulate table parsing rules Stopped byDOMPurify; CSP NoteThe only valid children of <table> are <caption>, <colgroup>, <col>, <thead>, <tbody>, <tfoot>, <tr>. Anything else is foster-parented. This is a defined part of the HTML5 parsing algorithm.
B. SVG/Style Raw-Text Context
MXSSSVG STYLE
03
<svg><style></style><img src=x onerror=alert(1)></svg>
ContextIn SVG context: style is raw text; in HTML context after round-trip: style is CSS, img follows as HTML Mechanism5 — Re-parse changes context: sanitizer sees img inside SVG/style (text), browser after innerHTML sees img as HTML BypassesSanitizers that serialize and re-check — the serialized form is the same; the re-parse is different Stopped byDOMPurify ≥ 2.0.17; Trusted Types; avoiding innerHTML round-trips NoteClassic mXSS pattern (Cure53 research). In SVG parsing context, <style> is a raw-text element — its content is text. When the full string is serialized and re-parsed in HTML context, <style> becomes CSS and ends at </style>, leaving the img as free HTML.
MXSSMATH STYLE
04
<math><style></style><img src=x onerror=alert(1)></math>
ContextSame as SVG/style but in MathML namespace Mechanism5 — MathML style element is raw text; re-parse in HTML context produces executable img BypassesSanitizers handling SVG/style but not MathML/style Stopped byDOMPurify; blocking MathML style; CSP NoteThe MathML namespace also treats <style> as raw text. Same mutation mechanism as SVG/style. Different namespace — may evade sanitizers that handle one but not the other.
C. <noscript> Scripting State
MXSSNOSCRIPT
05
<noscript><p title="</noscript><img src=x onerror=alert(1)>"></noscript>
Context<noscript> is parsed as HTML when scripting is OFF, as raw text when scripting is ON Mechanism5 — Parser state divergence: sanitizer runs with scripting OFF (sees this as HTML tree), browser with scripting ON (sees raw text) — or vice versa BypassesSanitizers that run with scripting in a different state than the target browser Stopped byDOMPurify (removes noscript); Trusted Types; ensuring sanitizer and browser use same scripting state NoteThe HTML5 spec defines noscript parsing differently based on the "scripting flag". With scripting ON: noscript content is raw text (no child elements). With scripting OFF: noscript is parsed as HTML. A sanitizer built on a scraping engine with scripting OFF parses a different tree than a JS-enabled browser.
D. <template> Inert Context
MXSSTEMPLATE
06
<template><img src=x onerror=alert(1)></template> <script> // Sanitizer sees template content as inert (no execution) // But app code clones and appends the template: const t = document.querySelector('template'); document.body.appendChild(t.content.cloneNode(true)); // NOW the img is live → onerror fires </script>
ContextContent inside <template> is inert — scripts and event handlers don't fire. But when template content is inserted into the live document, they activate. Mechanism5 — Inert-to-active transition: sanitizer checks template content in inert state; app code moves it to live document BypassesSanitizers that check template content but don't account for the activate-on-clone step Stopped byDOMPurify; sanitising at the point of insertion, not at the point of template creation; Trusted Types NoteThe <template> element creates a DocumentFragment with a separate document. Scripts/handlers don't fire there. When you do cloneNode(true) and append to live document, the payload activates. The sanitize-then-template-then-insert pattern has this gap.
E. Attribute Mutation
MXSSATTRIBUTE
07
<!-- Input string (appears safe — style only): --> <p style="font-family:'foo()bar';">text</p> <!-- After innerHTML round-trip, some browsers produce: --> <p style="font-family:'foo()bar'">text</p> <!-- The mutation here: quotes and semicolons may shift, potentially opening expression() injection in IE or other CSS-level payloads -->
ContextCSS style attribute mutation through innerHTML serialization and re-parsing Mechanism5 — CSS expression injection via mutation of style attribute quote handling BypassesSanitizers that pass style attributes with valid-looking values that become invalid or executable after mutation Stopped byBlocking style attributes entirely in sanitizer; CSS value allowlisting; CSP NoteStyle attribute mutation is browser-dependent. IE's expression() in CSS is the historic execution point. Modern browsers don't execute CSS expressions, but style mutation can still produce unexpected visual effects used in UI redressing attacks.
MXSSATTRIBUTE CONTEXT
08
<!-- Sanitizer sees this and passes it (img with safe alt): --> <img alt="&lt;/img&gt;&lt;img src=x onerror=alert(1)&gt;"> <!-- innerHTML serialization produces: --> <img alt="</img><img src=x onerror=alert(1)>"> <!-- Re-parsed: alt value closing quote followed by dangling attribute = second img fires -->
ContextHTML entity encoding inside alt attribute that becomes unencoded after innerHTML serialization Mechanism5 — Entity decoding on serialization + re-parse; the alt attribute "contains" HTML that leaks on re-parse BypassesSanitizers that see escaped entities in attribute values as safe text Stopped byDOMPurify; serializers that re-encode entities on output NoteinnerHTML serialization may decode HTML entities that were safe in attribute context. When the serialized string is assigned to innerHTML again, the now-unencoded content is parsed as HTML. This is the mXSS definition: safe input → unsafe output after one serialize+reparse cycle.
MXSSANNOTATION-XML
09
<math><annotation-xml encoding="text/html"> <img src=x onerror=alert(1)> </annotation-xml></math>
ContextMathML annotation-xml with HTML encoding — creates an HTML integration point inside MathML Mechanism5 — Namespace/integration point: sanitizer may model this as MathML text; browser parses content as HTML BypassesSanitizers that don't implement HTML5 annotation-xml integration point semantics Stopped byDOMPurify; blocking annotation-xml; CSP NoteHTML5 integration points: <annotation-xml encoding="text/html"> and <annotation-xml encoding="application/xhtml+xml"> switch the parser to HTML mode. Content inside is parsed as HTML — including event handlers. Sanitizers must implement this per the spec.
