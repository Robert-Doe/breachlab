Mechanism 1 — Tag Parsing

The browser parses a tag and executes its content

The simplest mechanism. A <script> tag tells the parser to hand everything until </script> to the JS engine. No user interaction, no events — execution happens at parse time.

Example payloads:

<script>alert(document.domain)</script>
<script src="/echo.js"></script>
Server-side version: Visit /reflect?q=<script>...</script> to see this reflected from the server. The browser parses the HTML response and executes the script immediately. No clicks needed.
Key constraint: <script> injected via innerHTML does NOT execute (HTML5 spec §8.4). But via server reflection or document.write(), it does. This is why DOM XSS (Mechanism 4) relies on event handlers, not script tags.
Mechanism 2 — Event Handler Attributes

Any HTML element can execute JS via event attributes

Event handler attributes (onerror, onload, ontoggle, etc.) run JavaScript when the browser fires that event. Critically: this works even when <script> is blocked and even when injected via innerHTML. 

<img src=x onerror=alert(document.domain)>
<details open ontoggle=alert(1)>
<input autofocus onfocus=...>
Why onerror is the workhorse: src=x deliberately fails — the browser fires onerror synchronously, immediately, with no user action. Works on img, video, audio, input[type=image], object. This is the most reliable zero-interaction execution vector after <script>.
Mechanism 3 — URI Scheme Evaluation

javascript: and data: URIs execute code when navigated to

Certain HTML attributes accept URLs. When the scheme is javascript:, the browser evaluates the URI body as JS in the page's origin context. Affected attributes: href, src, action, formaction, data, xlink:href. 

<a href="javascript:alert(document.domain)">click</a>
<iframe src="data:text/html,<script>alert(1)</script>">
Defence gap: Sanitisers that strip <script> and block event handlers often miss javascript: in href attributes. The payload looks like a normal link. Requires the user to click — but in a phishing context, that is trivial.
data: URI note: In a sandboxed iframe, this runs on the null origin — limited access. In an unsandboxed iframe on the same origin, it has full access to parent.document.
Mechanism 4 — DOM Sink Assignment

JavaScript APIs that turn strings into executed code or HTML

The most important mechanism for modern web apps. The payload never touches the server — it flows from a URL fragment, postMessage, or localStorage into a dangerous DOM property or function. No server-side fix can prevent this. 

innerHTML = '<img src=x onerror=alert(1)>'
eval('ale'+'rt(document.domain)')
location = 'javascript:alert(1)'
Source → Sink: DOM XSS requires a source (where attacker data enters JS) and a sink (where it executes). Common sources: location.hash, location.search, document.referrer, postMessage. Common sinks: innerHTML, eval, setTimeout(string), document.write, location. Module 09 maps every source–sink pair in detail.
Mechanism 5 — Context Escape & Re-parse

A payload that looks safe to a filter becomes dangerous when the browser re-parses it

This is the hardest mechanism to defend against. The attacker crafts input that a sanitiser parses as harmless, but when the sanitiser serialises its output and the browser re-parses that serialisation, the payload ends up in an executable context. The sanitiser and the browser disagree about what the HTML means. This is called Mutation XSS (mXSS).

A simpler form is just breaking out of a context by injecting the delimiter that closes it, then adding executable content after.

Context Break — Attribute Escape

Input lands in: <div title="[INPUT]">

" onmouseover="alert(document.domain)" x="
The " closes the title attribute. Then onmouseover= is a new attribute on the same div. The trailing x=" absorbs the original closing quote. No angle brackets used at all.

mXSS Preview — Namespace Mutation

Input passes sanitiser, mutates on re-parse:

<math><mtext></math><img src=x onerror=alert(1)>
The </math> closes the MathML namespace. Everything after it is parsed as HTML. A sanitiser that processes the MathML context separately may not notice the <img> that follows. Full mXSS coverage in Module 13.
