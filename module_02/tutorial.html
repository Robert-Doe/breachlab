Module 02 of 19

How Browsers Parse HTML:
The Attack Surface

Before you can inject anything, you must understand what the browser does with what you give it. The HTML parser is not a strict validator — it is a fault-tolerant recovery engine, and its recovery behaviour is the root of nearly every XSS vulnerability ever found.

Prerequisites

What you will build in this module

  • A JavaScript file (quirks.js) demonstrating 5 parser quirks

  • Hands-on observation of the browser silently repairing broken HTML

Concept 1 — The Browser Is Not a Parser. It Is a Recovery Engine.

A strict parser — like an XML parser — rejects malformed input. Give an XML parser an unclosed tag and it throws an error and stops. The browser's HTML parser does the opposite: it never rejects input. It applies a precisely specified error-recovery algorithm defined in the WHATWG HTML Living Standard (which runs to several hundred pages) and produces a valid DOM tree from whatever garbage you give it. This was a deliberate design decision in the early Web: web pages written by humans are full of mistakes, and browsers that refused to render them would lose market share to browsers that tried harder.

This forgiveness is a security disaster. Every security filter that processes HTML must parse it correctly to decide whether it is safe. But "correctly" means implementing the same recovery algorithm as the browser — and that algorithm is enormous, browser-specific in subtle ways, and namespace-aware (HTML, SVG, and MathML have different rules). A filter that uses a simpler parsing model will see a different HTML tree than the browser does. Payloads crafted to exploit that gap — appearing safe to the filter but dangerous to the browser — are the basis of an entire attack class called mutation XSS, studied in Module 13.

For now, the key insight is this: the browser's DOM is the ground truth, not the HTML string. A security analysis of any web page must ask "what did the browser build?" not "what did the server send?" This is why you open DevTools Elements panel, not View Source, when auditing for XSS.

PhD Insight — Differential Parsing The gap between how a sanitiser parses HTML and how the browser parses the same HTML is called a differential. Finding differentials is an active research method: you feed the same input to both parsers and compare their output trees. Any difference is a potential bypass. This is how researchers discovered the DOMPurify bypasses of 2019 and 2020 — they fuzzed sanitiser output against live browser behaviour using automated differential testing. Your lab's parser_demo.html is a manual version of this technique.

Concept 2 — The HTML Parsing Pipeline

When the browser receives an HTML document, it processes it through a four-stage pipeline. Understanding each stage tells you where injected content can enter the pipeline and what rules apply at that entry point.

1. Byte Stream Decoder
Converts raw bytes to Unicode characters. Encoding attacks (UTF-7, overlong UTF-8) can inject characters here.
→
2. Tokeniser
Reads characters and emits tokens: start-tag, end-tag, character, comment, DOCTYPE. Mismatched quotes or angle brackets confuse token boundaries.
→
3. Tree Builder
Assembles tokens into a DOM tree. Applies error recovery. Insertion mode (body, in-table, in-SVG…) determines which tags are valid where.
→
4. Script Execution
Script elements, event handlers, and javascript: URIs are handed to the JS engine. This is when XSS executes.

Injected payloads can enter at Stage 2 (if user input appears inline in the HTML stream), Stage 3 (if input is assigned to innerHTML in JavaScript — DOM XSS), or Stage 4 (if input reaches an eval() call). Each entry point has different rules and different effective defences.

The Tokeniser's Insertion Modes

The most important thing to understand about the tree builder is that it operates in different insertion modes. When the parser sees <svg>, it switches into "in SVG" mode, where different parsing rules apply. When it sees <math>, it switches to "in MathML" mode. These modes have different rules about which tags are allowed, how attributes are parsed, and when to switch back to HTML mode.

An attacker who injects HTML that triggers a mode switch can cause the parser to interpret subsequent content under unexpected rules. The <math><mtext></math><img> pattern exploits exactly this: the </math> closes the MathML context mid-stream and the browser transitions back to HTML mode, parsing whatever follows as HTML — even if a sanitiser thought it was still inside safe MathML. We demonstrate this in Quirk 2 on the demo page.

Warning — "I'll just check for <script>" Is Not a Defence After this module, the temptation is to build a filter that blocks <script> tags. Resist it. Every subsequent module in this course shows a payload that executes JavaScript without a single <script> tag. The only complete defence operates at the DOM level — controlling which strings reach dangerous sinks — not at the string-matching level. Module 17 explains this fully. For now, just observe.

Concept 3 — The Four Injection Contexts

Every XSS injection point sits in exactly one of four parsing contexts. The context determines which characters the attacker needs to achieve execution, and which characters a defence must neutralise. Learning to identify the context before choosing a payload — or before writing a defence — is the single most important analytical skill in this course.

Context 1 — HTML Body

The attacker's input appears directly in the document body, outside any tag. For example: <p>Hello, [INPUT]!</p>. Here a < character starts a new tag. The attacker can inject any HTML element — <script>, <img>, <svg> — with full control over its attributes. This is the most permissive context and the easiest to exploit.

Defence: HTML-encode < → &lt; and > → &gt;. The encoded characters display correctly but cannot create new tags.

Context 2 — HTML Attribute Value

The attacker's input appears inside a quoted attribute value: <div title="[INPUT]">. A < character here is just data — it cannot start a new tag while inside an attribute value. However, a " (double quote) closes the attribute value. After the closing quote, the attacker is back in the tag body, where they can add new attributes — including event handlers like onmouseover="alert(1)". Critically: no angle brackets are needed. The injection string " onmouseover="alert(1)" is a complete XSS payload without a single < or >.

Defence: HTML-encode " → &quot; inside attribute values. Never use single-quoted or unquoted attributes for user-supplied values.

Context 3 — JavaScript / Script Context

The attacker's input appears inside a <script> block: <script>var name = "[INPUT]";</script>. Inside a script block, the browser applies JavaScript tokenisation rules, not HTML rules. The dangerous sequence is </script> — the browser closes the script block immediately upon seeing those characters, regardless of whether they are inside a JavaScript string. An attacker who injects </script><script>alert(1)</script> closes the existing script block and opens a new one.

Defence: Never embed user-supplied data inside <script> tags via string concatenation. Serve dynamic data as JSON via a separate API endpoint, not inline in script blocks.

Context 4 — CSS / Style Context

The attacker's input appears inside a <style> block or a style="" attribute. Modern browsers cannot execute JavaScript from CSS injection alone (legacy IE expression() is dead). However, CSS injection is not harmless: using CSS attribute selectors and background-image URL requests, an attacker can exfiltrate data character by character — for example, stealing a CSRF token from a hidden input field without executing any JavaScript and without triggering any CSP violation. This technique is covered in Module 12.

Info — Context is Server-Side AND Client-Side These four contexts apply both to server-side reflection (the server embeds input into HTML before sending it to the browser) and to client-side DOM manipulation (JavaScript reads input and inserts it into the DOM). The context rules are identical. The difference is where the input enters the pipeline: server-side injection enters at Stage 2 (tokeniser); DOM injection enters at Stage 3 (tree builder via innerHTML) or Stage 4 (via eval()).

Concept 4 — Five Parser Quirks That Create Injection Opportunities

The following five quirks are demonstrated live on parser_demo.html. Open that page in a separate tab and have DevTools Elements panel visible while reading this section. For each quirk, try to predict what the browser will do before you look at the Elements panel.

Quirk 1 — Unclosed Tags Are Silently Completed

The browser closes every unclosed tag at the end of its scope. A filter that looks for balanced open/close tag pairs as a signal of "this is benign markup" gets fooled: <b>text (no closing tag) still creates a real, fully functional <b> element in the DOM. More dangerously: <img src=x onerror=alert(1) (no closing >) is silently completed by the parser — the event handler still executes.

Quirk 2 — Mismatched Nesting Is Reorganised

<b><i>text</b></i> has mismatched nesting — the close tags are in the wrong order. The browser spec defines exactly how to restructure this into valid nesting. Sanitisers that operate on the string before the browser sees it may produce a different tree than the browser produces from the same string. This discrepancy is the mechanism behind mutation XSS.

Quirk 3 — Unknown Tags Become Generic Elements with Full Event Support

<xss onmouseover="alert(1)"> creates a real DOM element — an HTMLElement with tag name "xss" — and that element fires the mouseover event handler. The tag name is completely irrelevant. Any string is a valid tag name in HTML5. Filters that allowlist known safe tags and reject unknown ones are correct in spirit but must be paired with attribute filtering, because even "safe" known tags like <div> and <p> execute event handlers.

Quirk 4 — Unquoted Attribute Values Are Valid HTML5

<img src=x onerror=alert(1)> uses an unquoted attribute value for onerror. This is valid HTML5. A filter that searches for onerror=" (with a quote) will not match onerror= (without a quote). The attacker deliberately uses whichever quoting style the filter doesn't check. You will practise this systematically in Module 12.

Quirk 5 — Tag-Soup Inside Attribute Values Can Escape the Attribute

Consider: <div title="</div><b>escaped</b>">. A string-matching filter might think the </div> inside the attribute value is safe because it's "just data". But the browser tokeniser still responds to the closing tag sequence — depending on the specific context and browser, content can escape from the attribute into the document body. This is the basis of dangling markup attacks and certain mXSS patterns.

Code Walkthrough — /parse-demo server route

lab_server.py — /parse-demo route (new in M02)
@app.route("/parse-demo")
def parse_demo():
    # request.args is a dict of URL query parameters.
    # ?html=<b>test</b> → request.args.get("html") == "<b>test</b>"
    # The default keeps the page usable without a parameter.
    raw = request.args.get("html", "<!-- supply ?html=... -->")

    # We f-string 'raw' directly into the page HTML.
    # This is textbook Reflected XSS — the exact pattern we will study
    # in Module 04. We do it intentionally here so you can see what
    # happens BEFORE we study how to exploit it.
    page = f"""<!DOCTYPE html>
<html>...
  <div class="injected">
    {raw}       <!-- INJECTION POINT -->
  </div>
...</html>"""

    resp = make_response(page)
    # Content-Type tells the browser to parse this as HTML.
    # Without this header, the browser might display it as plain text.
    # In Module 07 we study what happens when Content-Type is WRONG
    # (e.g., serving an SVG as text/html).
    resp.headers["Content-Type"] = "text/html; charset=utf-8"
    return resp
lab_server.js — /parse-demo route (new in M02)
app.get("/parse-demo", (req, res) => {
    // req.query is Express's equivalent of Flask's request.args.
    // It parses the URL query string into a plain object automatically.
    const raw = req.query.html || "<!-- supply ?html=... -->";

    // Template literal with direct interpolation — same problem as Python.
    // This is why "never build HTML by string concatenation" is the rule:
    // any user-supplied string can break out of its intended position.
    const page = `...<div class="injected">
    ${raw}
  </div>...`;

    res.setHeader("Content-Type", "text/html; charset=utf-8");
    res.send(page);
});

Code Walkthrough — quirks.js

public/quirks.js — addDemo helper
function addDemo(title, inputHTML, notes) {
  const container = document.getElementById("results");
  const card = document.createElement("div");

  // We use createElement + textContent to safely display the raw HTML
  // string as visible text (not rendered). textContent encodes < and >
  // so the string is never parsed as HTML — only shown.
  const inputCode = document.createElement("pre");
  inputCode.textContent = inputHTML;  // SAFE — not innerHTML

  // The rendered output box uses innerHTML intentionally.
  // THIS is what we are studying: what does the browser DO with this string?
  // Open Elements panel and inspect resultBox after each demo loads.
  const resultBox = document.createElement("div");
  resultBox.innerHTML = inputHTML;    // INTENTIONALLY UNSAFE — educational

  // ... card assembly omitted for brevity (see full file)
}
Tip — textContent vs innerHTML Notice the two assignments in addDemo: inputCode.textContent = inputHTML (safe — displays the string as text) and resultBox.innerHTML = inputHTML (unsafe — parses and renders it as HTML). This contrast is intentional. Every time you assign to a DOM property, ask yourself: "does this parse the string as HTML or treat it as text?" The answer determines whether you have introduced an XSS vulnerability. We will return to this question in Module 09 with a complete catalogue of DOM sinks.
